## 二 · 顾客身份：令牌，不是账号

四角色体系（viewer/operator/lead/manager）是给后厨员工的。顾客**没有登录
环节**（扫码点餐的现实就是这样），所以 `/api/customer/*` 用一次性桌台令牌：

```
POST /api/customer/session     → customer_token（secrets.token_hex(16)，纯内存）
GET/POST 带 customer_token     → 服务端按 token 过滤归属
```

**安全边界**（`test_api_customer.py::TestBoundary` 钉死）：

1. 顾客只能看**自己的**单（两桌互不可见，`TestPlace::test_两桌互相看不见对方的单`）；
2. 催别人的 item_id → **404 不是 403**（403 等于告诉陌生人「这单存在但不是
   你的」）；
3. 顾客令牌访问 `/api/orders`、`/api/staff`、`/api/params` 一律 401——
   customer_token **不是**登录令牌，不存在「碰巧通过」的路径；
4. 菜单不含 `recipe_id`/`station_kind`（顾客不该知道后厨怎么分工）。

令牌内存存储、重启失效：演示场景完全够（重新开桌即可），文档如实声明，
`TestSession::test_令牌重启后失效` 把口径钉死。

### 补充（11-14）：匿名 ≠ 其他端无法对单

开桌时服务端额外下发 `customer_ref`（桌号 + 令牌前 4 位，如 `T03-A1B2`；
未带桌号为 `G-A1B2`），随订单一路透出：

| 端 | 能看到什么 |
|---|---|
| 管理端 `/api/orders` / 订单看板 | `customer_ref`、`table_label`、`source=miniapp` |
| TFT 后厨队列屏 | 单号后挂 `3桌` 短标签；行数据带完整 `customer_ref` |
| 审计日志 | `customer.order` 的 `after.customer_ref` / `after.table_id` |
| 小程序「我的」/ 订单 / 详情 | 本桌的顾客编号 |

**边界（写论文时不要含糊）**：编号不是身份，不含姓名 / 手机号 / openid，
不落库，随服务重启失效；完整令牌绝不外发。顾客通知端点按 `order_no`
白名单过滤，别桌编号拿不到。`tests/test_customer_identity.py` 把这些断言钉死。
要真正按人识别，得加 `wx.login` 换 openid + 用户授权 + 会员表 + 隐私政策，
属于 §一明确划掉的范围，当前不做。

## 三 · 与三端共用一条状态机

**顾客通道零业务逻辑**：下单直接调 `OrderService.place_order`（价格快照、
配方版本锁定、沽清整单拒绝并列出全部沽清项），催菜直接调 `OrderService.urge`。
顾客下的单 `source="miniapp"`，出现在员工 `/api/orders` 和 TFT 队列屏——
**不是顾客单单独一套状态机**。

事件流同理：顾客下单/催菜 emit `kind="order"` 事件（与员工下单同款），
管理端看板、TFT 播报、顾客通知三端订阅同一条流。

## 四 · 为什么轮询而不是 WebSocket / SSE

A9-03 原文写「WebSocket 实时状态」。落地选**轮询**（订单 2s、通知 4s）：

| 方案 | 问题 |
|---|---|
| WebSocket | 小程序后台切前台要重握手；服务端是 ThreadingHTTPServer，长连接占一个线程，几个顾客就会耗尽线程池 |
| SSE | 小程序 `wx.request` 不支持流式响应；EventSource 不存在 |
| **轮询 2s** | 进度延迟上限 = 2s（顾客看「快好了」这种粒度足够）；与 A8 TFT 的 `/api/events?since=` 轮询**同构**，三端只有 Web 用 SSE |

## 五 · 接口清单（7 条，总 57 条）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/customer/session` | 开桌发令牌（匿名） |
| GET | `/api/customer/menu` | 菜单（砍内部字段，停售菜不上） |
| POST | `/api/customer/orders` | 下单（复用 OrderService） |
| GET | `/api/customer/orders` | 自己的单 + ETA 三档 |
| POST | `/api/customer/orders/items/{item_id}/urge` | 催菜（30s 限频 → 429） |
| GET | `/api/customer/trace?code=` | 溯源（公开只读） |
| GET | `/api/customer/notifications?token=&since=` | 通知（轮询模拟） |

外加一个**非 JSON 端点**：`GET /api/customer/trace/label.png?code=`
（server.py 专门分支返回 PNG 字节，匿名可扫；`tools/miniapp_check.py` ⑨
覆盖）。空 code 在 server 层前置拦——`label_png` 对空码会生成一张
「指向空码」的能扫的废图，不报错。

## 六 · 通知：订阅消息的轮询模拟（A9-06）

真机订阅消息需要：企业主体 + 模板 ID + 用户点击授权，三样都是 H4 之后的事。
模拟版数据流已经定型：

```
事件流（emit kind="order"） → CustomerService.notifications(token, since)
  → 过滤：kind ∈ {order, cooking, customer} 且 order_no/item_id ∈ 我的单
  → message 文案（"订单已受理" / "正在制作" / "已出餐" / "已催菜"）
```

环境报警、遥测、工单一概不进顾客通知（`TestNotifications::test_环境报警不进
顾客通知`）：顾客只关心自己的单，也避免后厨内部状态泄漏。

真机接法：`CustomerService` 加一个 `push()` 消费者调微信
`subscribeMessage.send`，数据流不动。

## 七 · 真机预览与发布路线（A9-07 / H4，11-13 更新）

### 7.1 已就位：测试用途 AppID（11-13）

`miniapp/project.config.json` 的 `appid` = **`wxe9190b8ab70df245`**。
它是 `wx` + 16 位十六进制的 18 位标准 AppID，**不是开发者工具里那个
「测试号」（TouristAppID）**——工具测试号只能在模拟器里编译，不能真机
预览、不能上传代码；这个注册得来的 AppID 可以真机预览/真机调试。答辩
用开发版足够，不必等企业主体。

> 用户给的原始串是 19 位 `awxe9190b8ab70df245`（开头多一个 `a`），落盘时
> 按标准 18 位格式取 `wxe9190b8ab70df245`。`tools/miniapp_check.py` 已把
> 「`wx+16hex`」与「非占位号」做成硬断言，防止答辩包里混回 `touristappid`。
> 若 19 位串确为账号实际 AppID，改 `project.config.json` 一行即可。

⚠️ **AppSecret 不进版本库**：当前顾客通道用内存桌台令牌，根本不需要
AppSecret；将来接 `wx.login` 换 openid / `subscribeMessage.send` 时只放服务端
环境变量。小程序前端代码包可被反编译，写进去等于公开密钥。

### 7.2 现在就能做：手机真机预览（开发版，不需要域名备案）

```bash
# ① 起服务：--lan 绑 0.0.0.0 并打印本机局域网 IP
python tools/miniapp_check.py --serve --lan

# ② 把 miniapp/config.js 的 BASE_URL 改成脚本打印的地址，例如
#    const BASE_URL = 'http://192.168.2.246:8848';
# ③ 微信开发者工具 → 导入 miniapp/（AppID 自动读 project.config.json）
# ④ 手机与电脑同一 WiFi → 预览扫码 / 真机调试
```

四个必查项，少一个就是「模拟器好使、手机白屏」：

| 项 | 说明 |
|---|---|
| 服务端绑定 | `ApiServer` 默认 `host=127.0.0.1`，只对本机开放；`--lan` 才绑 `0.0.0.0` |
| `BASE_URL` | 必须填电脑的局域网 IP；`127.0.0.1` 在手机上指手机自己 |
| 域名校验 | 工具「详情 → 本地设置」勾「不校验合法域名」（`urlCheck:false` 已配）；基础库 2.4.0+ 开发版可直接请求同网段 http IP，若仍报域名错，手机端打开「调试模式」 |
| 防火墙 | Windows 放行 TCP 8848 入站，否则手机端一直超时 |

**实测（11/13，本机）**：LAN IP `192.168.2.246`，绑 `0.0.0.0` 后
`GET http://192.168.2.246:<port>/api/customer/menu` → `200 application/json`。
网络链路已验证，模拟器与真机 UI 差异、扫码体验仍需人工逐页点检（差距报告 A6）。

> **排障入口**：页面报「网络不可用」时先跑 `python tools/miniapp_netcheck.py`
> （只读四层体检：端口 → 回环 → 局域网 → 代理/防火墙），或直接双击
> `tools/start_miniapp_server.bat`。11/13 09:50 的现场故障根因就是
> **8848 无监听、后端没起**，与 AppID/域名校验无关；详见
> `05_系统记录/20261113_小程序真机预览接线卡.md`「排障」一节。
> 注意本机 `HTTP_PROXY` 会让 `curl` 返回 502 假象，验证一律 `--noproxy '*'`。

## 八 · 已知边界（如实写）

- 顾客令牌内存存储：服务重启顾客要重新开桌（无持久化，也无找回）；
- 离线期间顾客端无缓存策略（小程序本来就是联网应用，断网显示「服务器
  暂不可达，稍后自动重试」）；
- 催菜限频按 (token, item) 记忆，恶意换 token 可绕过——演示场景无对抗
  需求，生产应按 IP/桌台限频；
- 通知只有轮询版，无真机订阅消息（§六）；
- 支付跳过（方案原文允许），金额只做展示；
- AppID 是**测试用途的注册 AppID**，不是工具测试号（§7.1）：能真机预览，
  但正式发布仍卡在备案域名 / HTTPS / 企业类目（§7.3）；
- 真机预览走的是局域网 http，只适用于开发版，不能写进论文「系统部署」章节
  当成生产方案。
