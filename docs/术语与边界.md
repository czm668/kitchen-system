# 术语与边界：告别"state 五义"

> 审查报告 §3 指出：讨论"状态"必须先问是哪个——`AppState`、规则闩锁、`KitchenRuntime`、
> `device`、`tft/terminal` 各有状态机。这份文档给每个词一个唯一名字与边界，
> 新人不必通读 `state.py` 847 行才知道"改状态"指什么。

## 一、五种"状态"的唯一命名

| 统一叫法 | 代码位置 | 生命周期 | 谁在读 | 不要叫它 |
|---|---|---|---|---|
| **AppState**（进程单例） | `src/kitchen/api/state.py::AppState` | 一个 API 进程一份，重启即重建（MySQL 落库除外） | HTTP 路由、SSE、AI 中枢 | "系统状态"、"全局状态" |
| **规则闩锁**（guard latch） | `src/kitchen/rules/state.py` 及各 `*Guard` 的 `tripped()` | 单帧内触发，人工复位才清 | 判定链、互锁编排 | "告警状态"（那是我故障工单） |
| **KitchenRuntime**（领域内核态） | `src/kitchen/runtime.py::KitchenRuntime` | 同帧内推进，可被 AppState 快照 | 安全判定、派单、过程执行 | "业务状态"（太泛） |
| **设备态**（device） | `src/kitchen/hal/device.py` 与驱动层 | 跟随现场信号，断网不影响 | HAL、recorder | "状态"（和 AppState 撞名） |
| **终端态**（terminal） | `src/kitchen/tft/terminal.py` | TFT 侧离线缓冲，恢复后同步 | TFT 屏、离线补传 | "离线状态"（那是 resilience 的） |

**命名约定**：代码里出现 `state` 形参时，若类型不是 `AppState`，必须带前缀
（`guard_state` / `runtime_state` / `device_state` / `terminal_state`）。`AppState` 专用 `state`。

## 二、两条时间轴（R5，别再混用）

11-18 的告警刷屏事故根因是把两条时间轴混用。现在方法名已经强制区分：

| 方法 | 时间域 | 用途 | 典型值 |
|---|---|---|---|
| `AppState.monotonic()` | 单调秒，从启动起算，不受 `time_scale` 影响 | 计时、超时、工单 `due_at` 判定 | 几十～几百秒 |
| `AppState.wall_epoch()` | 加速后的 epoch 秒 | 展示、落库、跨重启可比的审计时间戳 | ~1.7e9 |

- `process/*` 里各业务类的 `self.now() -> datetime` 是**第三条**、各自独立的时钟，
  用于业务域内相对判定；它不是 AppState 的方法，别和上面两条混。
- `R5 lint`（`tools/rule_lint.py`，挂 CI 第一关）禁止 `api/` 下再用 `state.now()` /
  `state.wall()`，也禁止把 epoch 传给名叫 `now` 的参数。

## 三、两个"写路径"不是两条通道

| 名称 | 职责 | 落点 |
|---|---|---|
| MQTT 接入层 | 把外部消息接进来（Inproc / Paho 双实现） | `src/kitchen/mqtt/{transport,gateway,publisher}.py` |
| recorder 持久层 | 把已判定的事实写库（SQLite / MySQL 双后端） | `src/kitchen/storage/recorders.py::RuntimeRecorder` |

它们不是重复实现：删掉接入层断 MQTT 与半实物扩展点，删掉持久层断跨重启审计。
`SqliteRecorder` 是旧名（保留兼容一版），新代码一律用 `RuntimeRecorder`——
类名不再暗示只支持 SQLite。

## 四、两种"备份"各管一摊

| 工具 | 对应后端 | 用在 |
|---|---|---|
| `tools/backup.py` | SQLite | `docker-compose.lite.yml` / 裸机快速验证 |
| `deploy/backup-sidecar.sh` | MySQL | `docker-compose.1g.yml` 云端三容器 |

## 五、AI 的边界（护栏，不可越过）

- **输出只有建议**：结果结构里没有 `approve` / `decision` / `amount`。
  异常归因不关阀、派单建议不下发、合规问答不改门禁。
- **既有 AI 场景**：`profile` / `support` / `finance_daily` / `compliance_daily` /
  `anomaly_explain` / `dispatch_hint` / `compliance_qa`，共 7 个，统一走
  `guest/llm.py::run_guarded` + `ai/specs.py::AdvSpec`。
- **新增场景只写 `AdvSpec`**（提示词 + 白名单 + 确定性离线规则）并加进
  `specs.py:SCENARIOS`，provider / 护栏 / 审计 / 管理端面板全部复用。
- 详见 [`13_多融合AI中枢设计.md`](13_多融合AI中枢设计.md)。

## 六、交付边界（答辩口径，不要越界宣称）

| 说法 | 能不能说 | 可辩护的表述 |
|---|---|---|
| "全链路闭环" | ⚠️ 要加限定 | 软件全链路闭环 + 硬件接口预留 |
| "生产级 MySQL" | ❌ | MySQL 8.4 单实例，1 GiB 机型参数调优，已验证跨重启持久化与每日备份 |
| "视觉模型已验证" | ❌ | 6 类轻量模型，4 类有验证集，uniform/phone 无独立验证样本 |
| "真机验证" | ❌（半实物/真机 0 条） | 驱动与互锁有单测与仿真回放，未整机装配 |
| "正式小程序上线" | ❌ | 开发模式与真机预览可用，正式版等备案域名 + HTTPS |

唯一宣称出口是 [`功能证据矩阵.md`](功能证据矩阵.md) 与
[`requirements.json`](requirements.json)，不要反过来改 README 造数字。
