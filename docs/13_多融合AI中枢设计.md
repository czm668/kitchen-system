# 多融合 AI 中枢设计（A28 扩展模块）

## 一、为什么是"中枢"而不是"再接三个模型"

学校明确"功能基本不删减，主要要求是多融合 AI"。项目里 AI 其实早有三处：顾客画像
与客服（`guest/`）、经营日报点评（`finance/`）、合规日报点评（`compliance/`），共用
`guest/llm.py` 的可插拔 provider。但两个问题会让"多融合"变成"多处各自接模型"：

1. 三个域直接调 provider，护栏只在 guest 完整，日报点评各写各的降级逻辑；
2. 新增场景没有统一入口，容易被某个模块直连模型 → 幻觉改业务状态、断网即 500。

所以做**中枢**：把"场景"抽象成 `AdvSpec`（提示词 + 白名单 + 离线规则），新增 AI 能力
只写一个 spec，其余（provider、护栏、审计、面板）全部复用。底层 `llm.py` 不反向依赖
业务域，依赖方向单向 `ai/ → guest/`，老链路零改动。

## 二、架构

```
        ┌──────────── 单一 provider (make_provider) ────────────┐
        │  有 key → DeepSeekProvider(live)  无 key → RuleProvider │
        └──────────────────────┬───────────────────────────────┘
                               │ 共用同一实例
   ┌──────────┬──────────┬──────┴───┬───────────┬──────────────┐
 guest      finance   compliance   ai/(新中枢)   vision/(视觉AI)
 profile    finance_  compliance_  anomaly_     detector.py
 support    daily     daily        dispatch_    （图像类独立，见证据矩阵）
                                   compliance_qa
        └──────────── 统一护栏 run_guarded ────────────┘
                               │
                     AiResult + llm_runs 审计
                               │
                 GET /api/ai/overview（一屏七场景）
```

## 三、六个护栏（不因"多融合"放松）

1. **AI 只出建议**：`AiResult` 无 `approve/decision/amount`，异常归因不关阀、派单建议
   不下发、合规问答不改门禁；
2. **必有离线降级**：无 key 时 provider 就是规则层，直接走场景自己的确定性规则；
  在线失败也降级到同一规则，不返回 500；
3. **结构化白名单**：分类/标签只能取 spec 白名单，模型自由文本只进 `summary/reply`，
  越界即降级；
4. **逐次审计**：`llm_runs` 记 model / prompt_version / latency / degraded_reason；
5. **不喂隐私**：路由层字段白名单 + llm 层二次过滤，openid/手机号/卡号/顾客 key 不出网；
6. **可复现**：`prompt_version` 随结果落库，同一 facts 与 mode 输出稳定。

## 四、三场景的"建议—业务"边界

| 场景 | 读什么（facts） | 输出 | 不改什么 |
|---|---|---|---|
| `anomaly_explain` | 规则引擎已判的告警类型、读数、门限、核查点 | 为什么判异常 + 人工复核建议 | 不关阀、不改告警状态 |
| `dispatch_hint` | 待派队列长度、空闲工位/人员数、人员池开关 | 先派哪单/是否改派的建议 | 不改订单与工位状态（`DispatchBoard` 裁决） |
| `compliance_qa` | 检查表六项的确定性结论、缺口明细 | 为什么达标/不达标、为什么不能出库 | 不改门禁、不改检查结论 |

三者的 facts 都是**聚合状态**，不是原始隐私数据；判定本身早已由确定性规则完成，
AI 只把结论翻译成人话并给复核提示。这是能回答"模型幻觉怎么办"的关键：幻觉也越不过
"只出建议"这道墙。

## 五、既有四场景只读聚合，不重复调用

`overview()` 从 `guest._llm_runs` / `finance._ai_runs` / `compliance._runs` 只读取值，
不重新跑模型、不重算日报快照。这样"一屏看七个场景"不会带来重复扣费或状态副作用。
单测用"一被调用就抛异常"的 provider 证明 overview 不触发任何在线调用。

## 六、接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/ai/overview` | `ai.read`（全员） | 七场景调用/降级/版本一屏聚合 |
| GET | `/api/ai/runs` | `ai.read` | 本中枢场景审计 |
| POST | `/api/ai/advise/anomaly` | `ai.advise`（组长+） | 异常归因建议 |
| POST | `/api/ai/advise/dispatch` | `ai.advise` | 派单优先级建议 |
| POST | `/api/ai/advise/compliance` | `ai.advise` | 合规问答 |

建议接口返回体带 `advice_only=true` 与 `slot_boundary`，前端必须把"建议"和"已执行"
在 UI 上分开表述。

## 七、单一数据源与守卫

`docs/requirements.json` 是功能行、AI 场景、规模数字的唯一事实源。
`tools/consistency_check.py` 做两层校验：

- **数据源 ↔ 代码事实**：路由数、迁移数、pytest 数、AI 场景数从代码自动发现；
- **数据源 ↔ README**：README 里的数字宣称必须与数据源一致。

改数字先改 JSON，再跑 `python tools/consistency_check.py --fix` 同步 README，
守卫在 `tools/ci.py` 第一关自动跑。

## 八、边界与答辩口径

- **"已落地"= 建议层已实现**，不等于对应硬件真机验证（硬件仍 0 条半实物）；
- 图像类 AI（着装/明火/留样识别）仍走 `vision/detector.py`，新增类别必须补验证集；
- 在线模型配 key 才启用，答辩现场无网/无限流也能全部用离线规则演示；
- 跟老师新要求对接：把新场景写成 `AdvSpec` 加进 `specs.py:SCENARIOS`，并在
  `requirements.json` 的 `features[].ai_scenario` 里引用，不要在各业务域直连模型。
