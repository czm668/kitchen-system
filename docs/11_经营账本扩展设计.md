## 一 · 为什么需要单独一个域

订单域回答「这桌点了什么、做到哪一步了」，客诉域回答「这单有什么问题、怎么补偿」。
**没有任何一层回答「今天赚了多少」**。核查确认：

- `routes.py` 里零 `export` / `report` / 日报 / 台账导出
- `web/src` 里零下载入口
- `dishes` 表只有 `price`，**没有成本价**
- `004_llm_reports.sql` 的 `reports` / `llm_runs` 两张表预留了日报与 AI 审计列，但在此之前**没有任何代码在用**

用户点名「流水、净利润计算很实用」，这一块既是空白，又正好能把前面两轮的成果
（`OrderItem.unit_price` 快照、A11 补偿凭证、LLM provider）串成一条真实业务链。

## 二 · 口径（写错就是假账）

### 2.1 什么算收入

| 情形 | 是否确认收入 | 理由 |
|---|---|---|
| 子项 `PENDING / DISPATCHED / COOKING / READY` | ❌ | 还没交付，下单 ≠ 收入 |
| 子项 `SERVED` | ✅ | 已上桌，经营口径的交付完成 |
| 子项 `CANCELLED` | ❌ | 退菜；`OrderItem.amount` 本身已返回 0 |
| 整单 `CANCELLED` 但个别子项 SERVED | 按子项判定 | 部分上桌的部分仍是已实现营业额 |

**项目没有支付链路**（`09_顾客端小程序设计.md` §一明确不做）。因此这里叫
「经营口径的已实现营业额」，**不是实收、不是银行流水**；所有接口、页面、
CSV 都带 `settlement_note` 说明。不造「结算状态」——无支付却造结算，等于假功能。

### 2.2 金额事实源

一律用 `OrderItem.unit_price`（A11 为客诉补偿加的下单快照）。菜品改价后历史账面
不变；`unit_price` 在这里是第二个用途。测试 `test_改菜价后历史账面不漂` 钉死。

### 2.3 成本

| 类别 | 来源 | 标注 |
|---|---|---|
| 食材成本 | 优先 `dish_costs.cost`（管理端逐菜维护）；未维护时 `售价 × 35%` | `manual` / `estimated` |
| 重做损耗 | 优先取该单已确认的食材成本；查不到按补偿金额 × 成本率 | `category=redo` |
| 期间费用 | 人工 / 房租 / 水电 / 其他，按日录入 | `overhead` |

35% 是餐饮行业常见食材成本率的演示取值，**不是核算结果**，界面与日报都标「估算」。
**历史账面冻结**：改成本率或标准成本只影响之后确认的账目，已落账行与 journal
重放都不重算（会计的历史不可变口径）。

### 2.4 核心公式（全部整数分）

```
revenue   = Σ revenue + Σ compensation(免单/优惠券，负向)
food_cost = Σ food_cost(负向) + Σ redo(负向)
gross     = revenue + food_cost
overhead  = Σ overhead(负向)
net       = gross + overhead
```

- 所有金额用 `Decimal` + `ROUND_HALF_UP` 量化成**整数分**累加，最后一次才转元；
  避免 `0.1 + 0.2 != 0.3`。
- 未录入期间费用时 `net == gross`，界面与日报**主动提示「不是完整净利润」**。
- 补偿冲减用**负数**表示（会计符号），不做绝对值包装。

## 三 · A11 补偿凭证的冲账（跨模块一致性）

| A11 `method` | 账目 | 方向 |
|---|---|---|
| `waive` 免单 | `kind=compensation, category=waive` | 冲减营收 `-amount` |
| `coupon` 优惠券 | `kind=compensation, category=coupon` | 冲减营收 `-amount` |
| `redo` 重做 | `kind=food_cost, category=redo` | 追加食材损耗，收入不动 |
| `none` / 未批准 | **不产生任何账目** | — |

只有 `state=approved` 且 `voucher_no` 非空的工单才冲账。幂等键按**凭证号前缀**
而不是 `kind` 判断——redo 记在 `food_cost`、免单记在 `compensation`，
按 kind 查会让重做凭证每次同步重复记一笔（实现时踩过，已写进测试）。

## 四 · 结构与持久化

```
FinanceService
  _entries: dict[dedup_key, LedgerEntry]   # 幂等键 = source_type:source_id:kind:category
  _costs: dict[dish_id, float]             # 手工标准成本
  _overheads: dict[biz_date, 4 项(分)]
  _ai_runs: list[dict]                     # 对齐 004::llm_runs 列名，定长 200
```

`sync()` 是**懒同步**：每个读接口前调一次，扫描订单子项与已批准凭证，
把新事实物化成账目，重复调用不重复记账。不侵入 `orders.py` 的状态机。

`finance_journal.jsonl` 追加三类记录（`entry` / `cost` / `overhead`），启动重放：

- 存的是**账目快照**而不是「订单 id 让启动时去查」：订单是内存态，重启后对象就没了
- `entry` 按幂等键后写覆盖；`overhead` 重放先撤当日旧账再按配置重建
- **重放不重新调 LLM，也不重算历史金额**
- 单行脏数据只跳过计数，不中断启动

## 六 · AI 日报的护栏

复用 A11 的 `LLMProvider`（`RuleProvider` 默认 / `DeepSeekProvider` 配
`KITCHEN_LLM_API_KEY` 启用），日报行按 `004::reports` 列形状输出
（`scenario='finance_daily'` / `model` / `prompt_version` / `latency_ms` /
`degraded_reason`），调用审计按 `004::llm_runs` 列名记录。**不另造表、不另造审计**。

六条硬护栏：

1. 金额全部由 `summary()` 确定性算出，**模型输出只写点评文字**，不参与计算
2. 只把聚合数字喂模型，**不喂 `guest_key` / 客诉原文 / 卡号 / 令牌**
3. 模型输出限长 400 字，夹带「批准 / 退款 / 修改金额 / 调整账目 / 执行关阀」等动作词一律拒绝并降级
4. 在线失败（超时/限流/解析失败）自动降级到离线规则层，记 `degraded_reason`
5. 当日 0 单明确输出「暂无经营数据，不做趋势推断」，不编造
6. 规则层输出**如实标 `mode=rule` 且带「非大模型生成」后缀**，不冒充 AI

这一步顺带把审查报告 §7「DeepSeek 未接」推进为「provider 与审计就位、
日报链路已通、配 key 即切 live」。

## 八 · 风险与常见坑（写进测试了）

1. **请求体别用 `method` 当字段名**：会和 `Router.call(method, path, ...)` 撞名
   （A11 已踩，本域用 `compensation` / `kind`）。
2. **新增迁移会打破硬编码基线断言**：本轮同步 3 处（迁移 15→16、表 46→49），
   并确认 `test_api_web_contract` 的写接口前端入口检查由 `FinanceView.vue` 里的
   URL 字符串自然通过，无需放宽白名单。
3. **期间费用重复录入是覆盖**：先删当日旧 `overhead` 账目再重建，
   journal 里 `entry` 与 `overhead` 两类记录交错时，重放顺序仍收敛到同一结果。
4. **重放阶段不碰 `state`**：`FinanceService` 在 `AppState.__init__` 装配期间构造，
   时钟/仓储可能尚未就绪，`_replay_overhead()` 刻意不依赖 `state`。
5. **后端是内存态**：改代码必须重启服务；重启后订单对象消失，但账目从 journal 恢复。
6. `npm run build` 在本机需把 `TMP/TEMP` 指到项目内 `.local/tmp/vite`（系统 TEMP 是
   8.3 短名，esbuild 删临时文件会被拒）。
