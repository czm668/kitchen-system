# 功能规格与联动阈值

> 17 条功能 · 实现级判据 · 版本 v1.0 · 2026-11-12
> 阈值均为**默认值**，可在管理端 `env_thresholds` 修改；端侧缓存 NVS，断网按最后配置执行。
> 标 🔧 的需要现场标定。

## 0. 全局规则

1. **两级动作**：`预警`（语音 + 小程序提示，不动作继电器）→ `联锁`（继电器动作 + 推送 + 工单）。
2. **安全类联锁不设人工等待延迟**，燃气超阈值立即关阀。
3. **单点超限只预警**，需多源交叉或持续时间满足才进联锁。
4. **燃气泄漏时不主动切断灶台电源**——继电器动作可能产生火花。
5. **恢复动作一律人工确认**，断网期间禁止自动恢复。

## 一、环境安全闭环（7 条）

### #1 燃气泄漏联动关阀与分级处置

| 项 | 内容 |
|---|---|
| 判据源 | `gas_level`（MQ-2，0~1 归一化） |
| 基线 | 滑动窗口**中位数**（抗脉冲干扰）；开机前 **5 分钟只建基线不判定**；基线**每周更新**并写 NVS（断电不丢） |
| 判定 | 按基线计算**浓度突变率**，不按绝对浓度 |
| 🟡 预警 | 浓度呈上升趋势但未超泄漏阈值 → 语音 + 小程序提示，**不动作** |
| 🔴 联锁 | 超过泄漏阈值 → 关燃气电磁阀 + 启动排风扇 + 声光语音报警 + 推送负责人 + 生成处置工单 |
| 复位 | 浓度回落 **且** 人工确认后复位 |
| 误报抑制 | 明火期间（火焰传感器有效）确认窗口延长至 **30 秒**、突变率阈值上调 |
| 用到的动作 | `gas_valve_close`(CH1)、`fan_on`(CH2)、`alarm_light_on`、`voice_play` |

⚠️ MQ-2 对酒精、烟雾同样敏感 → **只作泄漏趋势判定，不作绝对浓度报警**。

#### 实现落点与参数（`src/kitchen/safety/gas.py`，已落地）

判据分两层：`GasBaselineTracker` 只管基线，`GasLeakMonitor` 只管分级；框架能力（持续时长、闩锁、复位、持久化）复用 `kitchen.rules`，**不重造**。

| 参数 | 默认值 | 为什么是这个值 |
|---|---:|---|
| `window_sec` 基线窗口 | 300 s | 覆盖率 5 分钟内的正常波动；太短会被做饭节奏带偏，太长则跟不上季节变化 |
| `min_samples` | 60 | 2 Hz × 30 s。低于这个数，一个瞬时脉冲就能当基线 |
| `guard_ratio` 抗污染闸门 | 0.25 | 偏离当前中位数 >25% 的读数**不进窗口**。没有它，缓慢泄漏会把基线一起抬上去，形成「相对正常」的正反馈，气在漏而报警自己消失 |
| `absolute_threshold` | 0.55 🔧 | 现场标定。到了这个浓度就不是「油烟有点大」 |
| `warn_ratio` / `alarm_ratio` | 2.0 / 4.0 | 相对基线的增量：3 倍浓度算预警、5 倍算联锁 |
| `warn_ratio_flame` / `alarm_ratio_flame` | 3.5 / 5.0 | 明火期上调。**上限受绝对门限约束**：基线 0.08 时 6 倍会落到 0.56 > 0.55，该分支永远不生效，等于把明火期判成瞎子 |
| `duration_sec` / `duration_sec_flame` | 5 s / 30 s | 明火期确认窗口延长，避免厨师炒菜时误关阀 |
| `boot_grace_sec` | 300 s | 上电时灶台附近本就有残留气味，直接判定必误报 |
| 周更 | 7 × 86400 s 比较 | 用**时间差**不用日历周：设备停几天再开机，按星期几算会漏更新 |

两条纪律，写反了就是事故：

1. **先判定，再决定能不能进基线**。先 `update()` 再 `assess()`，泄漏 3 分钟后基线就涨到 0.55，报警自动消失。
2. **明火期放宽绝对门限是禁止的**。真到泄漏浓度跟有没有明火无关。

端到端演示：`python tools/gas_demo.py`（650 s 基线周更固化 → 1010 s 预警只播报 → 1170 s 联锁关阀 → 1560 s 人工复位放行）。

### #2 排烟积热预警

| 项 | 内容 |
|---|---|
| 判据源 | `hood_temp`（MAX6675 CH1 + K 型，0~1024℃） |
| 分档 | 由服务器 APScheduler 按时段下发，端侧缓存 NVS，断网按最后配置执行；管理端可远程改 |

| 档位 | 温度阈值 | 10 分钟温升 | 动作 |
|---|---:|---:|---|
| 营业（高峰） | > 280℃ | > 100℃ | **仅预警**（语音+小程序），不联动——避免影响出餐 |
| 备餐（低峰） | > 250℃ | > 80℃ | 启动排风机 + 关闭燃气电磁阀 |
| 收档（无人） | > 200℃ | > 50℃ | 启动排风机 + 关闭燃气电磁阀 + 生成清理工单 |

> **温度阈值与温升是两条独立判据，任一成立即触发（OR，不是 AND）。**
> 写成 AND 会留两个安全漏洞：缓慢升到 300℃ 却因为「10 分钟只涨 20℃」不报警；
> 快速冲到 200℃ 因为「没到 280℃」不报警。两条路都是真实存在的起火前兆。
> 落到配置上就是 `env_thresholds` 里**一档两行**（`kind=tier` 一行、`kind=window` 一行），
> 引擎逐条判定，天然是 OR。

> 「安全」与「不影响出餐」的矛盾靠分档拆开：高峰只提醒，低峰无人时才动手。
> 阈值可按实际调试标定 🔧。

#### 实现落点与参数（`src/kitchen/rules/schedule.py` + `src/kitchen/runtime.py`，已落地）

| 项 | 口径 | 为什么 |
|---|---|---|
| 下发内容 | **时段表**（哪个时段是什么档），不是「当前档位」 | 下发当前档位的话，断网那一刻档位就冻结：19:00 断网、22:00 该收档了，端侧还停在营业档（只播语音不联动），收档后无人时段的积热完全没人管 |
| 端侧计算 | 按本地时间 + 时段表自己算 | 断网只影响「表能不能更新」，不影响「现在该是什么档」 |
| 时段跨零点 | 支持，且按**起始日**归属 | 周一 22:00→周二 02:00 属于周一的时段；写反了会让「只排周一」的配置在周日凌晨生效 |
| 档位兜底 | 配置不明 → `closed`（最严档） | 宁可多关一次阀、多开一张清理单，也不能退回营业档只播个语音 |
| 配置缓存 | 档位表 + 阈值行 + 动作语义一起进 NVS，`sha256` 校验 | 阈值宁可旧，也不能没有；损坏时降级到内置默认并上报 `config_degraded` |
| 切档与规则重装 | 切档只 `set_profile()`，**不重装规则** | 重装会重置去抖计时：燃气泄漏（持续 30 s 确认）正计到 25 s 时切档，报警白等 30 s |
| 判据去抖 | 默认 3 s（窗口判据同样走） | `rise` 在旧点滑出窗口时会突变，没有去抖就是告警自己闪三下 |
| 同指标多判据 | 同等级只上报一条，其余边界并入正文 | 一次积热两条判据同时成立 → 两条一模一样的小程序告警 |
| 工单去重 | `(metric, ticket)` 一次事故只开一张 | 闩锁每 60 s 重报，不去重会开出几十张清理单，值班表被刷满 |


### #3 明火离人判定

| 项 | 内容 |
|---|---|
| 判据（AND） | ① 视觉连续 **10~15 秒**（可配）判定该工位无人 ② 该工位火焰传感器检测到明火 |
| 为什么 AND | 单靠视觉会误判（转身、遮挡）；单靠火焰会把正常炒菜当离人。**离人是必要条件** |
| 动作 | 关燃气电磁阀 + 声光语音报警 + **锁定该工位** |
| 复位 | 人员返岗**刷卡**后复位 |
| 延迟口径 | 视觉在岗判定延迟 1~2 秒；无人阈值 10~15 秒可配 |

#### 实现落点与参数（`src/kitchen/safety/flame.py` + `env_thresholds` id=22，已落地）

判据拆两处，各管一件事：**主判据**在 `env_thresholds`（`flame_b > 0.5` 持续 12 秒），
**「无人」**由 `kitchen_rules.json` 的 `requires` 做 AND。框架（去抖/闩锁/复位）仍走 `kitchen.rules`。

| 项 | 口径 | 为什么 |
|---|---|---|
| `duration_sec` | 12 s（文档 10~15 s） | 太短会被「转身取料」打到；太长则油锅起火的黄金处置期（约 30 s）已过半 |
| 视觉信号通道 | 内部注入，**不进 12 类遥测契约** | 它是 AI 推断，不是传感器读数；混进契约会让「遥测完整率」这个运维指标失真 |
| 视觉超时 `vision_timeout_sec` | 30 s | 超过即判定失联 |
| **失联时的取值** | 喂 `0`（有人），**不是 `1`（无人）** | 默认「无人」意味着一次网络抖动就关掉全店燃气阀、切断灶台电源——误停业的代价远大于它挡住的收益，于是没人敢开这个功能。降级的同时由 `vision_health()` 单独产出「视觉离线」告警：**降级要说出来，不能装作还在工作** |
| 刷卡复位 | 只解锁 `metric=flame_b` 的规则 | 不限定范围的话，一张工牌就能把「气还在漏」的燃气联锁按成正常——系统里最危险的越权路径 |
| `card_reset` | 仅 #3 声明为 `true` | 刷卡的语义**就是**「我人回来了」，而人回来恰是该判据失效的直接原因，等传感器反应过来才解锁会让厨师以为卡坏了。燃气不声明，所以「气还在漏就按确认」依然被拒 |
| 健康证过期（#9） | 允许复位，写 `warnings` 上送 | 过期是合规问题，现场处置是安全问题。合规事后追责，安全不能等 |
| 恢复文案 | 「判据已解除（flame_b=1，前置条件不再成立）」 | AND 规则恢复时主判据可能仍成立（火还在、人回来了）。说「已恢复正常（flame_b=1）」会让用户以为是误报 |
| 恢复事件的动作 | 空 | 「关闭」类动作再下发一次只会多关一次阀；真正的恢复（开阀、恢复供电）必须等人工确认 |

#### 真实视觉接线（`src/kitchen/vision/link.py`，A5-06 已落地）

`FlameVisionLink(guard, station_id=1)` 把一个 `FlameGuard` 接到一个灶上，只做三件事：

1. **按工位取人数**（`station_headcount[station_id]`），不按整幅画面。2 米外的服务员路过
   不能让灶前的火变成「有人看着」；按全画面人数的版本在「两灶 + 传菜口」的后厨里
   **永远不触发**，而且没人会发现。
2. `headcount == 0` → `no_person=True`。过道里的人不算任何工位有人。
3. **视觉离线时不调 `observe_vision()`**：离线还喂「有人」等于给瞎掉的防线续命
   （`_vision_at` 一直被刷新，`vision_health()` 永远在线），运维不会去修摄像头。
   不喂 → 守卫自己超时 → `vision_frame()` 按「有人」降级。


### #4 灶台占用采集与派单约束

| 项 | 内容 |
|---|---|
| 占用 | 厨师上灶刷工牌确认占用；出餐确认释放 |
| 校验 | 对应工位**火焰传感器校验是否实际点火**（刷卡占位但没点火要能发现） |
| 派单约束 | 已占用灶台**不重复派单**；空闲灶台优先给**交期最近**的任务；全部占用则新单排队 |
| 排风状态 | `sct_current`（SCT-013）采集排风机回路电流，判断排风系统运行状态——**仅监测，不做碳排核算** |

#### 实现落点与参数（`src/kitchen/process/dispatch.py`，已落地）

三个概念必须分开，合在一起就丢掉两个诊断能力：

| 概念 | 数据 | 少了它会怎样 |
|---|---|---|
| **派单** | `order_items.station_id` + 状态 `dispatched` | — |
| **占用** | `station_occupancy`（`state='open'`） | 与派单合并后，答不出「派了单但一直没人上灶」 |
| **点火** | 同一行的 `flame_verified` | 与占用合并后，答不出「刷了卡占住灶但没开火」——灶显示 busy、实际空着 |

| 项 | 口径 | 为什么 |
|---|---|---|
| 工位忙闲判定 | 以**会话/预约为准**，`work_stations.state` 只当缓存 | 重启后进程内会话没了、列里还写着 `busy`，表现是「重启后所有灶都占用中」 |
| 派单排序 | `Order.due_at` 升序 + 催菜提前 3 分钟 + 稳定次序 | 不稳定排序会让同一批单两次扫描换顺序，「为什么先做这单」无法复现 |
| 全忙 | **不派**，返回排队位置，不抛异常 | 营业高峰全忙是常态；抛异常会让前端每分钟弹一次错 |
| 点火窗口 `flame_grace_sec` | 30 s | 刷卡到拧阀通常 5~15 s；窗口内报「未点火」会让每次开火先弹一次假告警 |
| 点火阈值 | `flame_b ≥ 0.5`（与 id=22 同口径） | 两处各写一个门限，早晚会不一致 |
| 排风门限 | `sct_current ≥ 0.15 A` | 风机铭牌 0.4~1.2 A，待机读数 < 0.02 A，取中间 |
| 无读数 | 报 `unknown`，**不报停转** | 默认「停转」会让排风正常的今天也弹告警，几天后没人再看这条提示 |
| 排风是否拦派单 | **不拦** | 排风停了是 #2 的事（声光+联锁）；派单层再拦一次会让整条线派不出单，比积热更危险 |

### #5 冷链温度监测

| 项 | 内容 |
|---|---|
| 判据源 | `fridge_temp`（DS18B20 #1）、`freezer_temp`（DS18B20 #2） |
| 真实阈值 | 冷藏 **0~8℃**、冷冻 **≤ -18℃** |
| 确认窗口 | 超阈值需**持续 2 分钟**才报警 |
| 波动过滤 | 柜门短时开启导致的温度波动自动过滤 |
| 动作 | 分级超限报警 + 语音播报 + 生成工单 |

#### 实现落点与参数（`src/kitchen/safety/coldchain.py` + `env_thresholds` id=12/13/14/23/15/16/17/24，已落地）

**分级用两条阈值行叠加，不用一个「严重度」字段**：

| 级别 | 阈值行 | 确认时长 | 动作 | 工单 |
|---|---|---|---|---|
| 1 预警 | `range` 0~8℃ 之外 | 引擎默认 3 秒去抖 | 只播语音 | 不开 |
| 2 报警 | `duration` > 8℃ | **120 秒** | 声光 + 语音 | `cold_chain` |

两级的动作差异写在 `kitchen_rules.json` 的 `by_level` 里（`level=1` 与 `level=2` 各一套），
这样 real / demo 两套口径自动共享同一份动作语义，不必把 6 个 id 逐个列出来。

**开门波动过滤是波形识别，不是再调一个阈值**：

| 参数 | 默认值 | 依据 |
|---|---|---|
| `rise_window_sec` | 20 s | 升速只看最近 20 秒；用整段回溯窗算会被开门前的平稳期稀释 |
| `rise_rate_c_per_min` | 6 | 开门 8~15℃/min，压缩机故障 1~2℃/min，6 取偏保守一侧 |
| `jump_c` | 2.5℃ | 小于 2.5℃ 是除霜循环的正常起伏 |
| `hold_sec` | 120 s | 开门取货最长约 2 分钟；超时放行，交给「持续 120 秒」接住 |
| `recover_margin_c` | 1.0℃ | 回落到基线 +1℃ 即认定门关上（放进去的货本身是热的） |
| `escape_c` | 8℃ | 升幅超过 8℃ 只可能是故障，立刻放行 |

三条不能省的实现口径：

1. **过滤期间该指标不进 `metrics`**。引擎对缺数据的语义是「宁可不判」，正好用来冻结
   `duration` 计时——不需要给引擎加「暂停」这种新状态。
2. **过滤必须上送**（`FilterEvent.to_payload()`，`kind=cold_chain_filter`）。静默过滤等于伪造
   正常：平台上看不到曲线，事后也查不出「那天为什么没报警」。
3. **过滤有上限**（`escape_c` / `hold_sec`）。只写「凡陡升都放过」等于冷链彻底失效，所以还配了
   `tests/test_coldchain.py::test_门一直开着最终仍会报警` 这条用例把这条底线钉住。

### #6 留样柜温度与销毁提醒

| 项 | 内容 |
|---|---|
| 判据源 | `sample_temp`（DS18B20 #3） |
| 真实阈值 | 留样柜 **0~8℃** |
| 确认窗口 | 超阈值持续 2 分钟 |
| 销毁 | 留样满 **48 小时**生成销毁任务并推送小程序 |
| 演示加速 | 时钟加速：48 小时压缩为 **1 分钟**；真实运行按自然时间 |

#### 实现落点（`env_thresholds` id=18/19/20/25，已落地）

- 演示阈值 **25℃**（温水 35℃ 触发、常温水 22℃ 不触发），与 #5 同构同样分两级；
- 刻意**不闩锁、不开单**：留样柜超温要的是「当场听见」，真正的处置是查柜子，
  不是跑去按确认键。所以它的报警级也是 `latch=false`；
- 48h 销毁任务属业务动作（不在 9 个执行器动作里），落在 A4 的工单模块。

#### 实现落点（`src/kitchen/process/retention.py` 的销毁段，已落地）

- `destroy_due_at = sampled_at + 48h / time_scale`；演示 `time_scale=2880`（48h→60s），
  真实 `1.0`。**加速只折算到期时刻，不改判定逻辑**，演示与线上同一条路径；
- 销毁任务对应 `work_orders.type='retention_destroy'`，同时生成一条 `miniapp` 推送；
- 生成**幂等**（同一份留样只开一张单）：按秒扫描若不幂等，一分钟能开出上百张单；
- 未到期 `destroy()` 抛 `NotDueError`（提前销毁=撕证据链）；到期但扫描未跑到时**补开单**；
- 重复称重覆盖 `sampled_at` 并重算 48h——留样时间以最后一次达标上架为准。

### #7 后厨温湿度联动

| 项 | 内容 |
|---|---|
| 判据源 | `t`、`h`（DHT11） |
| 动作 | 超限联动排风扇 |
| 定位 | **辅助展示**，不列入主线演示，**不参与报警判定** |

> 明确降级为展示项：DHT11 精度 ±2℃/±5%RH，用于报警判定会拖累整体可信度。

#### 实现落点（`env_thresholds` id=21 + `kitchen_rules.json` 的 `t`，已落地）

- `level=0`（仅展示）但**动作照发**：超 35℃ 或低于 10℃ 就 `fan_on`；
- 它与 #1 燃气、#2 排烟**共用 CH2**，按 §6.1「任一触发即开、全部恢复才关」合并——
  这也是 A2-08 互锁框架的第一个真实用例（三源共用排风）。

## 二、人员准入闭环（4 条）

### #8 晨检准入

| 项 | 内容 |
|---|---|
| 触发 | 刷 RFID 工牌 |
| 问卷 | 体温、腹泻、咽部炎症、手部伤口 |
| 不合格 | 拒绝该工牌领取任务 + 语音拦截 + 管理端**锁定该员工当日操作权限** |
| 复核 | 组长复核通过后恢复：TFT 刷组长工牌 + 管理端二次确认，**双通道留痕** |

#### 实现落点与参数（`src/kitchen/staff/admission.py`，已落地）

一次刷卡要过**五道门，顺序即拒绝原因的优先级**：工牌 → 人员 → 健康证 → 当日排班 → 晨检 → 工位资质。

| 门 | 判定 | 拒绝码 |
|---|---|---|
| 工牌 | UID 归一化（去 `0x`/冒号、转大写）后查 `staff_cards` | `unknown_card` / `card_disabled` |
| 人员 | `staff.enabled` | `staff_disabled` |
| 健康证 | **任一**证件 `valid_to >= 当日`（不看 `state` 列） | `cert_missing` / `cert_expired` / `cert_revoked` |
| 排班 | 当日有班且未被 `blocked` | `not_on_shift` / `shift_blocked` |
| 晨检 | 当日记录存在且未锁定 | `morning_missing` / `morning_failed` |
| 资质 | 工位 `kind` 要求的资质**全部**覆盖 | `qualification_miss` |

三条不能换顺序的理由：

1. **先证后检**：证过期的人去填问卷，填完还是被拒——人会认为系统坏了，而不是证过期了；
2. **停用卡 ≠ 未登记卡**：前者是「换过卡」，后者是「没绑过」，现场处理方式完全不同；
3. **只有 `morning_missing` 才弹问卷**（`AdmissionResult.needs_morning_check`）。证件/卡类问题属硬门禁（`masked=True`），问卷不出现——填了也进不去，不给假希望。

**体温门限 37.3℃**（`MORNING_TEMP_LIMIT_C`），四项中任一项不合格即锁定当日权限。缺项（未填体温）
按不合格处理——与环境侧「缺数据宁可不判」方向相反，理由见 `staff/models.py` 的
`MorningAnswers.failures()`：环境误报的代价是白跑一趟，门禁漏检的代价是食安事故。

**复核**要求三件事同时成立：复核人持 `lead` 资质、**不能是本人**、TFT 刷卡 **且** Web 二次确认。
缺任一项即拒绝，且**不写半条留痕**（`channel` 只写 `tft+web`）。复核后 `result='excused'`，
原始不合格项仍保留在 `failures` 里供追溯。

### #9 健康证到期拦截

健康证台账到期 → 自动拦截排班 + 拒绝该工牌刷卡。APScheduler 每日扫描到期。

#### 实现落点（`CertificateSweeper`，已落地）

每日扫描 → 无有效证的人：证件 `state` 同步为 `expired`（**物化结果要跟日期一致**）、
当天及以后的排班置 `blocked` 并把原因写进 `shifts.assignment.blocked_reason`、
`warn_days=30` 提前给出临期提醒（办证要时间，到期当天才提醒等于逼人无证上岗）。

判定始终按 `valid_to` 而不是 `state`：扫描任务漏跑一次（服务重启、容器重建、时区变更），
`state` 就会漂移，「state=valid 但 6 月已过期」是真实会发生的形态。`state` 只用于列表筛选。

### #10 资质匹配派任务

配方工序所需资质 vs 刷卡人资质比对 → 不符则**不向该工位派发此工序**，改派资质匹配的在岗人员。

#### 实现落点（`AdmissionController.candidates()`，已落地）

候选集四个条件缺一不可：启用 → 资质覆盖（AND）→ 当日健康证有效 → 当日晨检已通过（+ 在岗）。

**候选集与准入判定必须用同一套条件**。只按资质筛，会把证过期的人派出去，再在刷卡时被拒——
那时工单已经派出去了，只能人工改派。工位资质要求直接取 `work_stations.kind`（种子即 `stove`），
不另建要求表：两个工位一种 `kind`，建表只会多一个必须同步的事实源；要按工序细分时走
`station_requirements` 覆盖，仍不改表。派单联调在 A4。

### #11 离岗检测与任务动态重排

| 项 | 内容 |
|---|---|
| 判据 | 视觉判定工位在岗状态，延迟 1~2 秒；连续离岗阈值 **10~15 秒可配** |
| 动作 | 该工位未完成任务按交期顺序转派其他在岗人员 + 刷新管理端甘特与 TFT 队列 + 语音与小程序通知 |
| 与 #3 区别 | #11 只管**任务重排**，#3 才动燃气阀。离岗不等于有明火 |

#### 实现落点（`src/kitchen/staff/duty.py`，告警侧已落地）

`DutyGuard` 把「在场」当状态积分，而不是当事件处理：`presence()` 每帧上报谁在哪个工位，
`tick()` 逐帧复查该人当日准入（复用 `AdmissionController.scan_staff()`，**不另写一套判定**），
连续违规满 `grace_sec=5` 秒才出 `DutyAlert`。

- **必须有去抖**：人刚刷完卡正要去填问卷、TFT 提交与视觉刷新有几秒错位、复核提交瞬间缓存还旧——
  没去抖的版本在联调时表现为「工位一直在响」，然后有人去把喇叭线拔了；
- **只开一张单**：同一人同工位在整个违规期间报一次（`alerted`），离开或准入恢复才清状态。
  按分钟重报会让工单里同一问题刷十条，人就开始忽略工单（A2 闩锁重报踩过这个坑）；
- **动作只有 `alarm_light_on` + `voice_play`**，工单类型 `unauthorized_on_duty`。
  不切电、不关阀——#3 才有资格动燃气阀，未授权上岗不等于有明火；
- 任务重排（转派、刷新甘特与 TFT 队列）依赖 A4 的任务表，本阶段只做告警与工单。

#### 任务重排（`src/kitchen/vision/absence.py`，A5-05 已落地）

| 项 | 口径 | 理由 |
|---|---|---|
| 离岗阈值 | 12s（文档 10~15），`AbsencePolicy.absence_sec` | 视觉在岗判定本身延迟 1~2 秒，取 10 秒实际只给 8 秒，蹲下取料就误报 |
| 只看有活儿的工位 | `occupant_of()` 返回非空才判 | 没人上灶的工位本来就没人在，那不叫离岗 |
| 责任人的两个时刻 | 占用会话 **或** 预约（`reserved_staff()`） | 只看占用会话时，「派了单还没走到灶前就跑了」会既不报离岗也不转派，单子挂在空气里 |
| 可转派 | `pending` / `dispatched` | — |
| **不可转派** | `cooking` → 只报「需组长接手看火」 | 炒到一半换人等于重做，锅里东西没人认账，出食安问题查不到责任人 |
| 接手人 | `matcher.candidates()`（四查）+ 不在忙 + 未预约 | 与派单、刷卡准入同源，不另立一套 |
| 无人可接 | **撤销预约、退回队列**并报原因 | 留着指向离岗者的预约会让那张单卡死 |
| 灶腾出来 | 立刻 `dispatch_pending()` | 只做转派的话，腾出的灶空到下一轮派单，现场看到「灶空着、单在等、系统没反应」 |
| 刷卡可救 | `mark_present()` 压过视觉 | 蹲在灶下修东西时视觉连续十几秒看不到人，#3 会关阀；刷卡比视觉硬 |

### #12 配菜称重防错

| 项 | 内容 |
|---|---|
| 流程 | TFT 显示本单所需食材与克重 → 配菜 → `weight_g`（HX711）核验 |
| 判据 | 偏差超过 **±5%** → 锁定下一步 + 语音提示 |
| 解锁 | 补足或更正后解锁 |

#### 实现落点与参数（`src/kitchen/process/cooking.py`，已落地）

| 项 | 口径 | 为什么 |
|---|---|---|
| 判据来源 | `dish_recipe_items.weight_g` + `tolerance_pct` | 改菜谱不该改代码 |
| 容差 | `max(目标×百分比, 1 g)` | 生抽 8 g 的 5% 只有 0.4 g，HX711 单次抖动 ±0.5~1 g。只按百分比判，小料「怎么放都锁着」，现场最后一定把容差改成 50% —— 那等于取消防错 |
| 边界 | 偏差 **> 5%** 才锁（正好 157.5 g 合格） | 文档写的是「超过 ±5%」 |
| 锁定范围 | 只锁**下一步**，不锁整单 | 已称完的项保留结论；全单锁死会逼人取消重下，留一堆废单 |
| 重称 | 覆盖上一次结论，不累加不取平均 | 称错了再称是常态，累加会让师傅永远修不回区间 |
| 负读数 | 直接拒绝并提示检查去皮 | 判成「少了 150 g」会把师傅引到配菜上，实际是 HX711 没去皮 |
| 留痕 | 每次称重一条 `process_events(kind='weigh')` | 日管控台账要按时间线汇总关键操作 |

### #13 工序 SOP 分步确认

TFT 按工序分步显示下锅顺序、火候、时间与**关键控制点（CCP）**；厨师逐步刷卡确认。
**关键步骤未确认不允许出餐。**

#### 实现落点与参数（`src/kitchen/process/cooking.py`，已落地）

| 项 | 口径 | 为什么 |
|---|---|---|
| 顺序 | 必须按 `step_no` 递增确认 | SOP 的意义就在顺序：先下锅后切配，菜是废的 |
| CCP 门禁 | 任一 `ccp=1` 未确认 → **拒绝出餐** | 不是提示，是门禁 |
| 身份 | `requires_card=1` 的步骤必须带 `staff_id` | 写进 `process_events` 的身份是事后追责与台账的唯一凭据 |
| 重复确认 | 幂等返回「此前已确认」 | TFT 双击很常见；报错会让人以为没生效，然后点第三次 |
| 出餐目标状态 | 只推到 `ready`，不直接 `served` | 上桌是传菜的动作；合成一步会把传菜时间混进出餐时长，而复核要看「菜何时离火」 |
| 阻塞原因的呈现 | `blockers()` **一次列全** | 逐条抛会让师傅「补一样、被拒一次」循环，现场直接打电话要求关掉系统 |

### #14 留样称重

按批次品种生成应留样品清单 → 扫码确认并称重 → 不足 **125g** 提示补足 → 达标后记录留痕。

#### 实现落点与参数（`src/kitchen/process/retention.py`，已落地）

| 项 | 口径 | 理由 |
|---|---|---|
| 应留样清单 | 按**当日生产**的批次（`dish_batches.produced_at`） | 按 `state='produced'` 取会把昨天的活儿天天重列，现场直接关掉页面 |
| 扫码输入 | 溯源码 **或** 批次号 | 只认溯源码时，漏贴标签的那盒就没法留样——而漏贴最常发生 |
| 达标门限 | `weight_g >= 125` | 124g 被拒（提示差多少克）、126g 通过，边界含 125 |
| 落库时机 | **只有达标才写** `retention_samples` | 不达标的也写进去，日报「留样合格率」会变成 100%，而实际没留够 |
| 不合格留痕 | 只进 `process_events(kind='retention', state='short')` | 追责要看「几点称的、差多少」，但不能污染留样台账 |
| 重复称重 | **覆盖**上次结论并重算 48h | 累加/取平均会让师傅永远修不回区间 |
| 负读数 | 直接拒绝并提示查去皮 | 判成「少了 125g」会把人引到配菜上 |

### #15 消毒曲线与复消闭环

| 项 | 内容 |
|---|---|
| 判据源 | `sterilize_temp`（MAX6675 CH2）+ 运行时长 |
| 达标 | **100℃ 以上累计保持 ≥ 10 分钟**（可按消毒方式配置） |
| 异常超温 | 超过 **150℃** 或运行时长超过设定上限 **1.5 倍** |
| 达标 | 记录留痕 |
| 不达标 | 生成**复消工单** + 该批餐具**禁止出库** + 语音提示；复消达标后关闭工单 |
| 生效时段 | **仅在消毒程序运行时段生效**——120℃ 属正常工艺温度，不触发报警 |

#### 实现落点与参数（`src/kitchen/process/disinfection.py`，已落地）

| 项 | 实现口径 | 理由（踩过的坑） |
|---|---|---|
| 门控 | 判定只在 `state='running'` 会话内；无会话时 `feed()` **丢弃读数并计数** | `env_thresholds` id=9 是 `range 100~120`，常温 25℃ 一进去就命中「低于下限」→ 不消毒时一直报警，现场必然把点关掉 |
| 达标累计 | 只有落在 **100~120℃** 才累加，满 600s 自动达标关单 | 125℃ 挂 10 分钟是**控温失效**（`hold_overtime`），不是合格；把高温也累计等于给故障发合格证 |
| 断点保护 | 单次采样累计上限 `max_gap_sec=120s` | 不设上限时，柜子断电 10 分钟再上电，一帧采样就「达标」 |
| 异常超温 | `>150℃` 立即判不达标 | 不等累计，避免真出事时还在「等 10 分钟」 |
| 超时 | 会话虚拟时长 `> 1.5×600s` 仍未达标 | 柜门没关/加热管坏，表现为「一直在跑但永远不达标」 |
| 禁出库 | 不达标 → `forbid_outbound=1` + 复消工单**成对出现** | 只禁不开单没人处理；只开单不禁，餐具照样出库 |
| 复消关单 | 复消达标 → 关单并把**原记录**的 `forbid_outbound` 清零 | 只解复消那条记录，`forbid_outbound(batch)` 仍读到 True → 「消合格了还出不了库」 |
| 演示加速 | `time_scale=20`：600s→30s | 与真实运行同一条代码路径，只折算时间 |
| 阈值来源 | `DisinfectionPolicy.from_thresholds()` 读 id=9/10/11 | 消毒柜换工艺（121℃ 高压）应改配置，不该重新发版 |

## 四、视觉识别闭环（1 条）

### #16 着装与行为违规

| 项 | 内容 |
|---|---|
| 判据源 | 近景摄像头（OV2640）+ 服务端 YOLOv8 |
| 识别目标 | 未戴厨师帽 / 未戴口罩 / 未穿工服 / 吸烟 / 玩手机 |
| 动作 | 生成违规事件 → **继电器切断该工位插座电源**（`power_cut`）+ 语音要求整改 |
| 复核 | 拍照复核通过后恢复供电：TFT 刷组长工牌 + 管理端二次确认，**双通道留痕** |
| 注意 | 这是**切断工位插座**，不是锁门——原电磁锁方案已按消防要求取消 |

#### 实现落点与参数（`src/kitchen/vision/`，已落地）

链路：`stream`（帧源）→ `detector`（YOLOv8，惰性依赖）→ `postprocess`（框 → 人员状态）
→ `violations`（跨帧去抖 → 事件）→ `evidence`（抓拍留痕）→ `disposal`（切电/语音/复核/工单）。

| 项 | 实现口径 | 理由（踩过的坑） |
|---|---|---|
| 类别表 | `person / hat / mask / uniform / cigarette / phone`，**顺序即 class id** | 顺序错 = 帽子认成手机，代码侧完全看不出来 |
| 正向证据优先 | **多人且帽子数 ≥ 人数**才判全合规 | 几何匹配失败的方向永远是「多报违规」；但单人走几何，否则「帽子挂腰上」也算戴了 |
| 穿戴匹配 | 附属框**落进目标区域的比例 ≥ 0.5** | 帽框只有头框 1/3 大，IoU 到不了 0.3，按 IoU 会让所有戴帽子的人被判没戴 |
| 工位归属 | 人框**底边中点**落在 ROI 内 | 人蹲下/俯身时中心点会跑到隔壁工位，决定「切哪个灶的电」 |
| ROI 划法 | 两灶之间**留过道**，不能左右对半分 | 对半分时每个脚点都落在某工位，「路过的人」被算成站在 ST1 |
| 去抖 | 连续 **3 帧** 且持续 **1.5 秒**（`ViolationPolicy`，可按帧率折算） | 只看帧数会在高帧率下退化成 0.4 秒；只看时长会在 1fps 抓拍下变成 2 帧 |
| 人离开工位 | **立即清零**；人在但合规，连续 3 帧才清 | 人走了状态还在 → 回来第一帧就报警（刚站回灶前就被切电）；一帧检出成功就清 → 3 帧规则永远凑不满 |
| 切电范围 | **只切行为类**（吸烟/玩手机），着装类只语音 | 没戴帽戴回来只要 3 秒，断插座不影响他戴帽子，却让整条线停摆 → 现场会去遮摄像头 |
| 切电去重 | 已断电的工位**不再发** `power_cut` | trip 分支每次 `reset_reviewers.clear()`，重复切电会冲掉组长已完成的确认 |
| 复核 | TFT + Web **双通道**，缺一不恢复；复核人须组长且**不能是本工位在岗人** | 视觉不知道画面里是谁，靠工位刷卡人判断——这条挡的是「自己刷卡把电送回来」 |
| 复核存储 | `reset_reviewers` 存**通道名**，人名记工单 | `confirm_manual_reset()` 的参数名叫 `reviewer`，但值要跟 `{"web","tft"}` 比对 |
| 恢复间隔 | 断电到恢复 ≥ **10 秒** | 立刻恢复等于没断过电，人没整改，形成「断电-恢复」循环，继电器触点会被打坏 |
| 证据包 | 多图 + 逐图 sha256 + 模型版本 + 判定参数；`meta.json` **最后原子写** | 只存图回答不了「哪一刻、谁判的、改没改过」；先写清单会留下「有清单无图」 |
| 工单 | 同一工位未关单时**复用**那张单 | 冷却期一过就开新单，工单中心里同一个灶挂十几条，值班的人会把通知关掉 |
| 视觉被遮挡 | 连续 20 空帧 + 工位仍有占用 → 单独报 `blind` | 离岗与「镜头被转开」在数据上都是 0 人，但处置完全不同 |

#### 硬件前提

- **摄像头独立 5V/2A 供电，绝不接工位插座**：切电后要拍到整改画面，否则双通道复核是形式主义。
- **一路继电器一个工位**（`StationPowerBank(capacity)`）：路数不够时抛 `PowerBusyError`，不静默错切。

## 五、异常兜底（1 条）

### #17 断网本地闭环与补传

**断网时端侧继续执行的三条保守保护**

| # | 保护 | 说明 |
|---|---|---|
| ① | 燃气浓度突变 → 立即关阀 | 不等网络 |
| ② | 排烟/消毒超温 → 联动风机 | 不等网络 |
| ③ | 火焰持续超设定时长（真实 **60 分钟**，可配；演示压缩为 **60 秒**）且期间无任何刷卡/按键/工序确认 → 关气源 + 语音「疑似长时间无人看管」 | 无人看管的最后兜底 |

**停用项**：断网期间**明火离人判定停用**（依赖视觉），管理端标记「视觉离线，离人检测不可用」。

**数据**：业务数据与本地日志进本地队列，恢复后带时间戳**批量补传并按 `seq` 去重**。

**界面**：TFT 显示「离线模式」红色边框。

**恢复**：补传完成后**自动重启视觉判定**。

### #17 实现落点（11/12）

| 设计要求 | 实现 | 位置 |
|---|---|---|
| 断网/掉电期间业务数据进本地队列 | 有界 JSONL 队列 + 侧车 `.state` | `resilience/queue.py` · `LocalQueue` |
| `seq` 唯一（服务端 `(device_id, seq)` 去重） | 装载时 `max(日志最大 seq, state.last_seq) + 1` | `queue._load()` |
| 安全类记录不被容量挤掉 | 关键配额 + `lost_critical` / `lossy` 上报 | `queue._make_room()` |
| 掉电半行修复 | 逐行解析失败即跳过并计 `truncated_lines` | `queue._load()` |
| 批量补传 | `batch_size` / `max_batches` 分块 | `resilience/upload.py` · `ReplayUploader` |
| 去重与冲突区分 | `MemoryOfflineStore.receive()` 返回 accepted / duplicates / conflicts | `upload.py` |
| 冲突处理 | 冲突记录不 ack、保留队列、本轮停止 | `ReplayUploader.replay()` |
| 时钟校准 | 最小 RTT + 连续一致才采纳，跳变上限 300s | `upload.py` · `ClockCalibrator` |
| 保护①燃气突变立即关阀 | 绝压 0.55 或基线 2 倍，连续 2 采样点 | `resilience/guards.py` |
| 保护②超温联动风机 | 罩温 280℃ / 消毒柜 130℃，滞回 5℃ | `guards.py` |
| 保护③长烧无人关气源 | 火焰 3600s ÷ `time_scale`，与最后人工活动取晚者 | `guards.py`（`time_scale=60` → 演示 60 秒） |
| 三条保护不经规则引擎 | `ConservativeGuards` 独立于 `env_thresholds` / 档位 | `guards.py` |
| 传感器故障工单 | 卡死 / 超量程 / 心跳丢失 → `work_orders.type='sensor_fault'` | `resilience/health.py` |
| 超时升级 | `due_escalations()` 轮询，接单后不再升级 | `health.py` · `FaultTicket` |
| 三端降级标记 | `build_degrade()` → `channels{tft,web,miniapp}` | `resilience/degrade.py` |
| 端到端装配 | 保护 → 引擎 → 互锁 → 入队，`tick()` 无网络 IO | `resilience/offline.py` · `OfflineFirstRuntime` |

**三条硬口径**

1. **`tick()` 里不做网络 IO**：`#1` 确认窗口 30 秒、`#3` 12 秒，而 HTTP 超时默认 3~10 秒；
   同步上传会把采样间隔拉长到十几秒——保护还在，窗口全乱。补传走独立的 `flush()`。
2. **冲突 ≠ 重复**：同 seq 同内容静默 ack；同 seq 不同内容说明端侧 seq 被复用，是真 bug，
   必须保留数据并停下补传，否则丢得无声无息。
3. **释放必须产出 `EVENT_RELEASED`**：保护只在跃迁时产出事件，漏了释放事件，互锁通道的
   触发源永不注销，`restore()` 一直返回「还有触发源」——现场表现是阀关了再也打不开。

**硬件前提**：队列落盘需要 NVS/Flash 有 ≥256KB 可用空间（2000 条遥测帧 + 500 条关键记录）；
真机写坏块由 LittleFS 兜底，**本机只验证了文件系统路径**（`LocalQueue` 接受任意 `Path`）。

## 六、互锁优先级与共用末端

### 6.1 三条共用规则

| 执行末端 | 共用触发源 | 开 | 关 |
|---|---|---|---|
| 排风扇（CH2） | #1、#2、#7 | 任一触发即开 | **全部恢复才关** |
| 工位插座（CH3） | #3、#16 | 任一锁定即断电 | **全部复核通过才恢复** |
| 燃气电磁阀（CH1） | #1、#2、#3 | 任一危险成立即关 | **人工确认后**复位 |

### 6.2 优先级

1. 燃气泄漏（#1）> 明火离人（#3）> 排烟积热（#2）> 视觉违规（#16）
2. 高优先级闩锁期间，低优先级的恢复动作**不得释放**同一通道。
3. CH1 开阀、CH3 恢复供电、工位解锁，**三者都必须人工确认**。

A2-08 实施时追加了两档**辅助优先级**（`channels.py`）：

| 优先级 | 取值 | 覆盖指标 | 说明 |
|---|---|---|---|
| P4 设备类异常 | `PRIORITY_EQUIPMENT=4` | #5 冷藏/冷冻、#6 留样柜、#15 消毒柜 | 只共用 CH2 与声光，不驱动 CH1/CH3 |
| P5 环境舒适 | `PRIORITY_ENV_COMFORT=5` | #7 温湿度 | 辅助展示，最低 |

插在 P3 之后不改变契约里四档的相对顺序，也不会让设备类异常压过安全类异常。
**未登记的指标按 P99 处理，但不会因此绕开互锁**——优先级只影响抢占，不影响是否受约束。

#### 编排层的三条实现口径（`src/kitchen/safety/interlock.py`，已落地）

1. **触发源必须是 `rule_id`**。`InterlockController.request(action)` 不传 `source` 时记成
   `anonymous`，三个功能先后开排风、只恢复一个，`anonymous` 会凑成「全部恢复」→ 风机在
   燃气还在漏的时候被关掉。
2. **恢复动作不携带优先级**。恢复的判据是「通道还有没有源」，不是「谁的源」——所以
   排烟（P2）自己好了也不许释放被燃气（P0）占着的通道。
3. **状态型动作去重、事件型动作不去重**。`fan_on` 已开就不再发；`voice_play` 每次都要播。
   `alarm_light_on` 按 `(通道, 状态键)` 记状态，GPIO_SIGNAL 上的声光与语音互不覆盖。

### 6.4 阈值配置的四条硬约定

`env_thresholds` 是唯一的阈值来源，但它有几个列容易被用错，写反了**不报错、只是永不触发**——这类问题在答辩前一周才暴露基本救不回来，所以单独定死：

1. **边界方向**：只填 `upper_bound` → 高于即违规；只填 `lower_bound` → 低于即违规；两个都填 → 落在区间外即违规。
   所有「超温 / 超浓度」阈值必须填 `upper_bound`。填成 `lower_bound` 会变成低温告警。
   （单测 `test_超温类阈值方向正确` 直接扫种子数据锁死这一条。）

2. **`kind` 决定时间维度，不是四种表**：
   `range` 瞬时值 · `tier` 瞬时值但限档位 · `duration` 需持续 `duration_sec` · `window` 用 `window_sec` 内 `aggregate` 聚合值。
   每种都必须自带边界，`duration` / `window` 行单独存在也必须有 `lower_bound` 或 `upper_bound`。

3. **`profile` 一列两种用途，必须分清**：
   | 用途 | 取值 | 何时变 | 例子 |
   |---|---|---|---|
   | 档位（tier） | 营业 `business` / 备餐 `prep` / 收档 `closed` | 运行时按 APScheduler 切换 | #2 三档阈值 |
   | 取值口径（dataset） | 真实 `real` / 演示 `demo` | 部署时选定，运行期不变 | #5 演示 5℃ ↔ 真实 -18℃ |
   
   两套阈值同时存在库里，靠代码区分维度（`Rule.profile_kind`），**不靠改数据**。
   混判的后果是：只传了档位名，所有 `demo`/`real` 规则被当成「别的档位」过滤掉，一条阈值都不生效且不报错。

4. **`level` 决定动作级别**（§0.1 两级动作）：`0` 仅展示（#7）· `1` 预警只播报 · `2` 联锁动继电器 · `3` 最高级。
   安全类联锁（燃气超门限）配 `duration_sec=0`，不等去抖——但这是安全决策，必须写在配置文件里看得见（`fixtures/kitchen_rules.json` 的 `by_rule`），不藏在代码默认值里。
