# 数据库设计

> MySQL 8 · 8 个业务域 · 设计基线 **29 张新建表 + 1 张扩字段表 ≈ 30 张**（001–014 时期）
> · **当前实测：17 份迁移 / 50 表 / 71 索引**（A11–A13 追加 015–017 后，见 §6 补记）· 版本 v1.2 · 2026-11-15
> 表名与用途以 `proj/docs/kitchen-contract.md` §3.3 冻结契约为准，本文不另立口径。

## 1. 设计原则

1. **新表一律 014+ 追加**，用 `CREATE TABLE IF NOT EXISTS`。001–013 已建表**不改结构**，
   只通过 `device_id` / `user_id` 等外键引用。
2. **不删表、不删列、不删 id**。指标停用走 `deprecated` 状态，历史读数保留。
3. **既有表优先扩字段，不新建影子表**。`detector_events` 用「只增列」方式补证据链与处置状态。
4. **派生状态不入遥测表**。视觉在岗、刷卡身份、互锁状态、离线标记走事件表或 `env_points.state`。
5. **状态机必须有事件流水表**（`order_events` / `process_events`），流水是唯一事实源，
   主表状态是流水的物化结果。
6. **补传去重键是 `(device_id, seq)`，粒度必须逐条**。批次粒度做不到「重复补传同一条
   不落两次」，所以用 `offline_records`，`batch_uid` 只作分组列。
7. **新表一律显式写 `COLLATE=utf8mb4_unicode_ci`**。只写 `DEFAULT CHARSET=utf8mb4`
   会按字符集默认规则建成 `utf8mb4_0900_ai_ci`，与 001–013 的表跨列比较报 1267。

## 3. 四张核心状态机

### 3.1 互锁状态（`env_points.state`）

| From → To | 触发 | 守卫 |
|---|---|---|
| `normal → latched` | 任一触发源命中 | 燃气泄漏 / 明火离人 / 排烟积热 / 视觉违规，**任一即开** |
| `latched → releasing` | 触发源恢复 | 该 `latch_key` 下**全部**触发源恢复 |
| `releasing → manual_reset_required` | 需人工确认 | CH1 开阀、CH3 恢复供电、工位解锁 |
| `manual_reset_required → normal` | 人工复位完成 | RC522 返岗刷卡 / Web + TFT 双通道复核 |
| 任一 → `degraded` | 断网(#17) | 端侧按 NVS 最后配置执行三条保守保护 |
| `degraded → latched` | 恢复后状态回放 | 补传去重后按最后有效状态接续 |

**闩锁口径**：每个执行通道独立维护 `latch_key` 触发源集合；**任一触发即开、全部恢复才关**；
高优先级占用期间，低优先级恢复动作不得释放该通道。

### 3.2 工位占用

`idle → occupied`（刷工牌上灶）→ 火焰传感器校验实际点火 → `occupied → idle`（出餐确认释放）。
占用期间视觉离岗超时 → 任务转派但**占用不释放**（人可能只是短暂离开），返岗刷卡恢复。

### 3.3 订单

状态流转全部落 `order_events`，主表 `orders.status` 为其物化结果；并发用 `version` 乐观锁。
交期 `promised_at` 决定派单优先级。

### 3.4 工单

`open → assigned → processing → reviewing → closed`；
整改类必须「复核通过」才闭合，复消类必须「复消达标」才关单。

## 4. 索引与性能

| 场景 | 索引 |
|---|---|
| 遥测按设备+时间查 | `sensor_readings(device_id, metric, ts, value)`（010 已建，比 `(device_id, ts)` 更优） |
| 订单按状态+交期扫 | `orders(state, promised_at)` |
| 工位实时占用查询 | `station_occupancy(station_id, state, ended_at)` |
| 留样到期扫描 | `retention_samples(state, destroy_due_at)` |
| 离线补传去重 | `offline_records(device_id, seq)` **唯一** |
| 台账按期查询 | `daily_ledgers(ledger_date)` |
| 健康证到期拦截 | `health_certificates(valid_to, state)` |
| 视觉违规待处置 | `detector_events(scenario, disposal_state, ts)` |

> **MySQL 没有部分索引**。早期写法 `station_occupancy(station_id, released_at IS NULL)`、
> `retention_samples(expire_at)` 是 PG 语法；MySQL 上用 `(station_id, state, ended_at)` 与
> `(state, destroy_due_at)` 等价实现，查询侧固定带 `state='open'` / `state='pending'`。
> 以上索引由 `tools/migrate.py check` 实核列覆盖，不靠人看。

遥测表数据量最大，按**月分区**或定期归档到历史表；演示规模不必要，留作生产化建议。

## 5. 迁移纪律

1. **从 014 起追加**，一个迁移一个主题，不合并。
2. MySQL 不支持 `ADD COLUMN IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`：
   迁移器把「对象已存在」错误码（1050 表 / 1060 列 / 1061 索引 / 1091 删索引）识别为**幂等成功**。
3. 每次迁移必须能**重复执行**且结果一致（幂等）；回滚靠备份，不写 `DOWN` 脚本。
4. 结构变更后跑一次 `git diff -- migrations` 确认没动 001–013。
5. **迁移器只看列覆盖、不看索引名**。索引名自由命名，覆盖哪些列才是实质
   （如 `uk_offline_dev_seq` 是 UNIQUE 约束生成的自动索引，名字里没有 `seq`）。
6. **校验链**：`python tools/migrate.py check` 把 MySQL DDL 翻译成 SQLite 方言真执行两遍，
   核对 29 张表齐全、每表有主键、外键无悬空、必需索引覆盖列、`detector_events` 只增列、
   新表带 `COLLATE`。本机没有 MySQL 服务端，这是唯一能真验证 DDL 的手段。
