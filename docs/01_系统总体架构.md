│  管理端 Web(Vue3+ECharts)   顾客端小程序      后厨端 TFT(LVGL)        │
└───────────────┬──────────────────┬──────────────────┬───────────────┘
                │ HTTPS / WS       │ HTTPS            │ SPI 本地

│  服务端（Docker）                                                    │
│  FastAPI ── REST / WebSocket                                        │

│  规则引擎 ── 阈值·区间·档位·时长·闩锁（多源交叉）                     │
│  调度引擎 ── 订单→工位派单、占用约束、离岗重排、交期排序              │

│ ESP32                        │   │ OV2640 推流 → 服务端              │
│ 采集：DHT11 / DS18B20×3 /    │   │ 独立 5V/2A + 任务看门狗           │

## 2. 为什么拆两个 ESP32 节点

| 原因 | 说明 |
|---|---|
| 供电隔离 | ESP32-CAM 推流瞬时电流可达数百 mA，与继电器吸合共用电源会拉低电压导致复位——这是最容易在联调阶段炸掉的问题 |
| 职责分离 | 视觉只负责采流与推流；工位终端负责实时控制。视觉侧卡顿不影响继电器动作 |
| 看门狗策略不同 | 视觉节点要容忍长时间推流阻塞（启用任务看门狗），控制节点要求硬实时响应 |

esp-01s 取餐叫号屏为**可选项**，不进入主线演示。

## 3. 数据流

### 3.1 遥测上行

```
传感器 → 驱动 sample() → 平铺 payload → MQTT tele/<主题> → 服务端落 sensor_readings
                                         └→ 规则引擎实时判定
```

7 个遥测驱动、12 项指标、各自主题：

| 驱动 | 指标 | 主题 |
|---|---|---|
| `ambient` | `t`、`h` | `tele/env` |
| `gas` | `gas_level` | `tele/gas` |
| `thermal` | `hood_temp`、`sterilize_temp` | `tele/thermal` |
| `coldchain` | `fridge_temp`、`freezer_temp`、`sample_temp` | `tele/cold` |
| `flame` | `flame_a`、`flame_b` | `tele/flame` |
| `current` | `sct_current` | `tele/current` |
| `scale` | `weight_g` | `tele/weight` |

### 3.2 指令下行

```
规则命中 → 生成命令 → MQTT → 节点 B 执行 → ACK 回传 → 回写 devices.state
```

9 个动作、2 个执行驱动（`relay3ch` 6 个 + `signal` 3 个），**动作名与通道绑定是冻结契约**，
见 `05_接口与通信契约.md` §3。

### 3.3 事件流

视觉判定、刷卡、称重会话、SOP 确认、离线补传都走**事件**而非遥测：
`detector_events` + `process_events` + `order_events` 三处落点，各自带 `actor` 与 `channel`。

> 派生状态（视觉在岗、刷卡身份、互锁状态、离线标记）**不是遥测指标**。
> 这条口径必须守住，否则 `sensor_readings` 会被塞进一堆非数值状态。

## 4. 规则引擎能力边界

现有平台规则引擎表达不了本项目的 13 个判定点，需扩展 7 项能力：

| 扩展 | 用在哪 |
|---|---|
| `per_rule` 时长条件 | 冷链超温持续 2 分钟、消毒累计 10 分钟 |
| 窗口聚合 | 10 分钟温升 > 100℃ |
| 区间判定 | 消毒 100~120℃ 达标区 |
| 档位（时段）阈值 | 排烟营业/备餐/收档三档 |
| 多源交叉（AND/OR 组合） | 明火离人 = 视觉无人 AND 火焰有效 |
| 闩锁 + 人工复位 | 三通道「任一触发即开、全部恢复才关」 |
| 端侧执行 + NVS 快照 | 断网时规则继续跑 |

## 5. 调度引擎

```
新订单 → 交期排序 → 找空闲工位（已占用不重复派）
        → 校验资质匹配（配方工序所需资质 vs 刷卡人资质）
        → 派单 → TFT 队列刷新 + 语音播报
        → 离岗超时 → 未完成任务按交期转派在岗人员 → 甘特与队列刷新
```

约束：

- 已被占用的灶台**不重复派单**；空闲灶台优先给交期最近的任务；全部占用则新单排队。
- 厨师上灶刷工牌确认占用、出餐确认释放，**火焰传感器校验是否实际点火**（刷卡占位但没点火的异常要能被发现）。
- 资质不符**不向该工位派发此工序**，改派资质匹配的在岗人员。

## 6. 断网降级

| 层 | 断网时行为 |
|---|---|
| 端侧规则 | 继续执行三条保守保护：① 燃气突变仍立即关阀 ② 排烟/消毒超温仍联动风机 ③ 火焰持续超设定时长且无任何刷卡/按键/工序确认 → 关气源并语音提示 |
| 视觉 | **停用**离人检测；TFT 显示「离线模式」红色边框；管理端标记「视觉离线，离人检测不可用」 |
| 数据 | 业务数据与本地日志进本地队列，恢复后带时间戳批量补传，按 `seq` 去重 |
| 恢复 | 补传完成后**自动重启视觉判定**；期间人工动作留痕 |

断网期间**禁止自动恢复**供电/供气，全部走人工确认。

## 7. 部署形态

单机 Docker 编排：`emqx` + `api`(标准库 HTTP 服务，见 `07_管理端Web与接口契约.md`) + `mysql` + `vision`(YOLOv8)。
演示用笔记本/学生云主机均可，数据库与应用同机（api + MySQL 同机，见 docker-compose）。本毕设聚焦单机演示形态，**存储引擎自设计起即定为 MySQL 8**（见 `03_数据库设计.md`），nginx/HTTPS 等规模化生产加固不在本次范围（不指 MySQL 本身）。
