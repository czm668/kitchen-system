> 触发：用户「再想想还有什么没做完的功能但是必须有，扩展的功能可以提升项目的深度」。
> 定位：**补齐题目另一半的必需闭环**，同时把 17 条主线串成一条可举证证据链。
> 代码：`src/kitchen/compliance/` · `src/kitchen/api/compliance_api.py` ·
> `migrations/017_compliance_credential.sql` · `web/src/views/ComplianceCredentialView.vue`。

## 一 · 为什么这是「必须有」而不是第 18 条功能

核查实码结论（`05_系统记录/20261115_功能提升候选清单与优先级评估.md` §2 ④）：

- 17 条主线**判据全部落地**，每条有独立测试；再加一个业务域边际收益已经很低。
- 但题目叫《…后厨智能调度与**食安合规**管理系统》，合规侧只有
  `ComplianceView.vue` 的 4 个**查询页签**（晨检 / 健康证 / 资质 / 批次）；
  全局（排除 A12 刚做的经营 CSV）**零导出、零日报、零一页纸追溯**，
  `004::reports` 在 A12 之前没有任何代码在用。
- 也就是说系统「能查」，但**交不出凭证**。答辩问「合规体现在哪」，只能指屏幕。

所以 A13 不新增业务动作，只把分散在 8 个事实源的既有结论聚合成三样交付物：

| 交付物 | 作用 |
|---|---|
| 每日合规检查表 | 6 项逐项给「事实数 / 达标数 / 缺口明细」，可导出 CSV 存档 |
| 批次追溯一页纸 | 原料 → 留样 → 消毒 → 出库门禁 → 工单 → 审计的合并证据链 |
| 合规日报 | 按日归档快照 + 点评，复用 `004::reports` 与 A11 的 LLM provider |

**学术深度在哪**：它把「智能调度」与「食安合规」这两半从孤立模块黏成一条链，
论文第 5 章可以拿这张一页纸直接讲「一次出餐经过了哪些合规门禁」，
比再堆一个页面有实证价值。

## 二 · 六项检查的硬口径（写错就是伪造合格）

| 项 | 事实源 | 达标判据 | 易错点 |
|---|---|---|---|
| 晨检准入 | `staff_repo.morning_check` | 全员有记录且未被 `locked` 卡住 | 待复核 ≠ 放行；`admitted` 与无需复核都算通过 |
| 健康证有效期 | `staff_repo.certificates` | 当日 `is_valid_on` | 30 天内到期只标 `warn`，过期才 `fail` |
| 留样达标 | `retention.samples` + `dish_batches` | 当日**生产批次**各有 ≥125g 达标留样 | 清单按 `produced_at` 日期，不按 `state='produced'`（否则昨天的活儿天天重列）；不足 125g 根本不落台账 |
| 消毒达标 | `disinfection.records` | 已结束会话 `state == 'passed'` | **只信域层结论，不重算温度**：100~120℃ 累计 600s 才达标，125℃ 是控温失效；`running` 不计入判定 |
| 工单处置闭环 | `health.tickets` + `disinfection.tickets` + failed 记录 | `state == 'closed'` | 消毒不达标的记录本身也是一张未闭环工单 |
| 出库门禁 | `disinfection.records.forbid_outbound` | 无处于禁止出库状态的批次 | 复消清零后历史查不到「曾经禁过」，所以只表达当前状态 |

### 三条不可让

1. **空数据不是 100% 达标**：`checked == 0` 一律标 `na`、`rate = None`，
   不进达标率分母，也不参与「通过」。演示环境经常没跑消毒/留样，
   把这些算通过就是一张假合格证。
2. **不做加权总分 / 合规分数**：6 项量纲不同（人数 / 证数 / 批次数 / 会话数），
   加权系数是拍脑袋。只给逐项结论与整体 `pass / warn / fail / no_data`。
3. **不重算业务判据**：阈值、时长、门限全部由 #8/#9/#14/#15 域层判定，
   本模块只读结论。自己再实现一遍，等于造第二套判定逻辑，两套迟早打架。

## 三 · 一页纸追溯

`dossier(batch_id)` 合并：批次 + 供应商 + 溯源码 + 留样记录 + 消毒会话 +
出库门禁（`outbound_blockers`）+ 相关工单 + 操作审计留痕。

关键设计：**取不到数据的环节进 `missing` 并如实列出，不静默省略**。
省略会让一页纸「看起来完整」，实际是漏了证据——这是合规交付物最忌讳的。
`evidence_note` 明写「由域层既有记录实时聚合，未重新判定阈值；演示环境为仿真数据，
不能作为法定追溯凭证」。

## 四 · 日报与 AI 护栏

- 列形状复用 `004_llm_reports.sql::reports`，`scenario='compliance_daily'`，
  与 A12 的 `finance_daily` 共用一张表和同一套
  `model / prompt_version / degraded_reason / latency_ms` 审计列。**不另造表**。
- 默认离线规则层，点评只复述检查表结论，文案带「非大模型生成」；
  设 `KITCHEN_LLM_API_KEY` 后切 `DeepSeekProvider`，**只有 `mode == 'live'` 才调模型**。
- 在线失败（超时 / 解析失败 / 输出夹带动作词）一律降级，记 `degraded_reason`，
  绝不拖垮交付。
- 喂给模型的只有聚合数字与缺口标签，**不含姓名、卡号、顾客 key**。
- AI **不改检查结论、不判定合格、不代替检验**；护栏词表拦「批准 / 退款 / 判定合格」等。

## 五 · 权限、持久化、接口

| 项 | 口径 |
|---|---|
| 权限 | `compliance.read` = manager + lead。组长要拿表去现场核缺口；viewer / operator 不给 |
| 接口 | 5 条全 GET：`checklist` / `dossier` / `report` / `export` / `runs` |
| 为什么全 GET | 检查表是已有事实的只读物化，做成 POST 会让人误以为「点一下就完成了一次合规检查」。日报虽写快照，但那是按日幂等的留痕，不是业务动作 |
| 持久化 | `compliance_journal.jsonl` 追加重放，检查表/日报按日期覆盖；**重放不重调 LLM** |
| DDL 017 | `compliance_check_snapshots`（1 张表，2 索引）。表数 49→50，迁移 16→17 |
| 前端 | 独立页「合规凭证」（第 13 页），不与 4 个查询页签混在一起——检查表是每日交付物，节奏不同 |

## 六 · 明确没做

- 法定检验报告 / 监管接口上报（需资质与真实数据）
- 合规评分、风险等级自动处置（拍脑袋 + 越权）
- 补录/篡改历史检查表（快照生成后不回改，重生成留痕）
- 把本模块算进论文 17 条主线（时间账零缓冲，放「扩展实验」一章）
- 批次与人员的实名追溯（当前是匿名/工号口径，见 A11 会员边界）
