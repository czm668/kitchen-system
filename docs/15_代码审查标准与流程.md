# 代码审查标准与流程

> **一句话**：机器管"能自动判的"，作者管"自己该担的"，审查者只管"两者都兜不住的"。
>
> **适用对象**：`kitchen/` 工程内全部改动——`src/` `web/` `miniapp/` `deploy/` `migrations/`
> `tests/` `docs/` `tools/`。
>
> **与现有资产的关系**：本文不替代任何现有机制，而是把它们编排成一条可执行的链路：
> `tools/ci.py`（自动化关卡）→ `.github/pull_request_template.md`（作者自检）→ 本文（人审与门禁）
> → `05_系统记录/20261119_项目审查报告.md`（规则来源 R1–R6）→ AI 六护栏（`docs/13`）。

---

## 0. 为什么现在要立这个标准

不是代码写得差，是**没有人对"改完是否成立"负责**。三条已核实的事实（口径：2026-11-19 审查报告）：

| 事实 | 数据 | 后果 |
|---|---|---|
| 零评审 | 27 次提交直推 `main`，0 PR / 0 Issue / 0 功能分支 | 每个改动只有一个视角；错误口径能长期潜伏 |
| CI 连红 3 次 | 根因是两条测试**自己写错**（`session_uid` 传参、`business_writes` 前提） | "全量测试全绿"不等于正确，自证式测试会骗人 |
| 文档双份真相 | 至少 11 处数字靠手抄 | 答辩现场一被追问就穿帮 |

反过来，工程已有的自动化其实很强（`tools/ci.py` 多道关卡、`pre-push` 钩子、R5 时钟守卫、
`consistency_check` 数字守卫）。**所以本文刻意不做"再来一套通用规范"**——
只补上缺失的人审层，并且明确规定：**凡是机器能判的，一律不许写进人审清单**。
清单一旦混入风格意见，就会退化成"审查者心情"，最终没人看。

## 1. 三层防线：谁审什么

| 层 | 责任人 | 成本 | 覆盖什么 | 不通过的后果 |
|---|---|---|---|---|
| **L0 机器** | 无人 | 0 人力 / 约 3 min | 语法、时钟口径、文档数字、迁移连续性、前端构建、小程序配置、全量单测 | CI 直接红，**不进人审** |
| **L1 作者自检** | PR 作者 | 10–20 min | 影响面、契约变更、演示口径、回滚方案 | 自检未填完，**不许提审** |
| **L2 人审** | 审查者 | 20–40 min | 设计取舍、边界条件、安全模型、可辩护性、可维护性债务 | P0 未清零，**不许合并** |

三层之间是**门禁关系**，不是并列关系：

```
改代码 → L0 绿（tools/ci.py）→ L1 填完（PR 模板）→ L2 通过（P0=0）→ 合并 main
             ↑ 红了就回去修，不占用审查者时间
```

**这条顺序本身就是标准**：让审查者看一个 CI 没过的 PR，是浪费双方时间；
让机器去判"缩进对不对"，是把人当 lint 用。

## 2. 严重度分级（全项目统一用语）

审查意见**必须**带级别，否则作者无法判断该不该改、能不能合并。

| 级别 | 定义 | 典型场景 | 处理要求 |
|---|---|---|---|
| **⛔ P0 阻断** | 会造成数据丢失、越权、凭据泄露、答辩当场被证伪，或违反 AI 六护栏 | 凭据入库；`close()` 吞掉 commit 异常；AI 输出含 `approve`；文档宣称"生产级"而部署是裸 IP | **必须修**，修完复审该点 |
| **🔴 P1 必修** | 逻辑/契约/错误处理有实质缺陷，但非即刻事故 | 新增写接口没做鉴权；迁移改了历史文件；离线兜底未覆盖；硬编码阈值 | **本次修，或开 issue 并写明理由与期限** |
| **🟡 P2 建议** | 可维护性、性能、重复、命名 | 文件超阈值仍在增长；N+1 查询；两处近似逻辑可抽取 | 可合并，**记入债务表**，不阻塞 |
| **💭 P3 记录** | 个人偏好、风格、替代方案 | "我会用 dataclass 而不是 dict" | 只记录，**永不阻塞**；同类出现 3 次才升级为规则 |

三条铁律：

1. **P0/P1 必须写"为什么"和"怎么改"**，只给结论的评论等于没审。
2. **P3 不得阻塞合并**。用 P3 卡人是审查者的问题，不是作者的问题。
3. **P0 数量是合并门禁的唯一硬指标**：`P0 == 0` 才允许合并。

## 3. 通用检查清单（人审用，8 类）

每类给的是**问句**，不是"要检查 X"这种废话。审查时按影响面挑相关的类，不必逐条打卡。

### 3.1 正确性
- 这个函数在**空输入 / 单元素 / 超大输入 / 重复调用**下分别返回什么？有没有测？
- 边界是开区间还是闭区间？阈值是 `>` 还是 `>=`，和 `docs/04_功能规格与联动阈值.md` 一致吗？
- 失败路径返回的是"默认值"还是"错误"？把失败伪装成成功是本项目历史第一大坑（静默成功）。

### 3.2 数据与一致性
- 这个写操作是**原子**的吗？中途抛异常会留下半条记录吗？
- 双后端（SQLite / MySQL）语义一致吗？方言分支给了理由吗？
- 重启后数据还在吗？内存态与落库态谁是权威？（本项目多数业务态仍是内存，改这块必须显式说明）

### 3.3 安全与权限
- 新接口属于哪个角色？`test_api_auth.py` 有对应用例吗？
- 入参是否校验类型/范围/长度？是否直接进了 SQL、文件路径、shell、模板？
- 日志/审计里有没有明文口令、token、openid、手机号？（`api/audit.py` 的 `_MASK_KEYS` 是否覆盖到新字段）

### 3.4 错误处理与降级
- 外部依赖（LLM / MQTT / MySQL / 摄像头 / 串口）挂了会怎样？**有没有确定性兜底**？
- 宽 `except` 是"记录并继续"还是"静默吞掉"？后者必须有注释说明为什么可以吞。
- 异常信息会不会把内部栈返回给前端？

### 3.5 并发与时间
- 有没有共享可变状态没加锁？`ThreadingHTTPServer` 下这段代码会被几个线程同时进？
- 用的是 `monotonic()` 还是 `wall_epoch()`？（R5，混用曾导致告警刷屏事故）
- 定时任务重叠执行会怎样？有没有幂等键？

### 3.6 可维护性
- 新人能在不看作者的情况下读懂**为什么**这么写吗？（本项目注释风格是"解释决策"，不是"翻译代码"）
- 改一个阈值/常量要动几个文件？散落的魔法数字是否该进 `env_thresholds` 或常量模块？
- 这段逻辑是否已有实现？（`guest/` `finance/` `compliance/` 三域有相似结构，容易复制粘贴分叉）

### 3.7 性能
- 有没有 N+1 查询、循环内 IO、每请求重建大对象？
- 1 GiB 机型上这段内存占用可接受吗？（部署约束是硬约束，不是理论值）

### 3.8 测试
- 断言来自**契约或外部期望**，还是"实现怎么写就怎么断"？（后者是自证测试）
- 失败时能定位到具体原因吗？还是只报 `assert False`？
- 用例能离线跑吗？会不会依赖本机路径、真实网络、真实时钟？

## 4. 本项目专属硬规则（CR-01 … CR-14）

这一节是**可勾选条款**，也是审查意见里唯一允许引用的规则编号。
`R1–R6` 沿用审查报告既有编号，不重编；`CR-xx` 是本次新增的审查层规则。

| 编号 | 规则 | 违反的样子 | 自动化落点 |
|---|---|---|---|
| **CR-01** | 凭据不入库 | 新增 `*.key` / 真实口令 / API Key 进 git；`.env` 被 `git add -f` | `.gitignore`（`.env` `var/` 已覆盖）；人工确认 |
| **CR-02** | 契约唯一源 | 另建一份"接口清单"；在文档里重抄路由数 | `docs/requirements.json` + `scenarios/kitchen.json` |
| **CR-03** | 数字不手抄（R4） | README 里写死"51 表 / 93 接口" | `tools/consistency_check.py` |
| **CR-04** | 起来了 ≠ 成了（R1） | 只验 health 200 就说"页面正常" | `deploy/verify-cloud.sh` + 内容断言 |
| **CR-05** | DDL 必须存量验证（R2） | 只在空库跑迁移；改历史迁移文件 | `tools/migrate.py check` |
| **CR-06** | 部署改动双验（R3） | 只改 yml 不跑 `compose config`；只本地不云端 | `pre-push` 钩子 |
| **CR-07** | 两套时钟不许混（R5） | `now=state.wall_epoch()`；`state.now()` | `tools/rule_lint.py` |
| **CR-08** | AI 六护栏不许放松 | AI 结果里出现 `approve` / `decision` / `amount`；异常时关阀；未审计 | `tests/test_ai_fusion.py` + 人工 |
| **CR-09** | AI 新增场景只加一行 | 为加场景去改订单/派单/门禁状态机 | `specs.py:SCENARIOS` |
| **CR-10** | 降级必须可演示 | 依赖挂了就 500，没有确定性兜底 | 人工 + 用例 |
| **CR-11** | 写接口必须声明角色 | 新 POST 只校验登录不校验角色 | `tests/test_api_auth.py` |
| **CR-12** | 写操作必须落审计且脱敏 | 新增写接口没进 audit；新敏感字段未进 `_MASK_KEYS` | `api/audit.py` |
| **CR-13** | 演示口径必须显式声明 | 默认口令/占位驱动/脚本注入检测，PR 里不说清 | `accounts.py` 的启动告警 |
| **CR-14** | 范围冻结 | 顺手新增第 8 个业务域 / 第 N 张表，未先改 `requirements.json` | 人工 |

**CR-13 补充**：本项目允许演示默认口令（`DEFAULT_PASSWORD`）与占位驱动（`ScriptedDetector`），
但**必须同时满足**：运行期有 WARNING 日志 + PR 描述里写明"这是演示口径" + 文档不宣称"已实测"。
三者缺一即 P0——这不是代码问题，是**可辩护性**问题。

## 5. 分域清单

### 5.1 Python 服务端（`src/kitchen/*/`）

| 检查项 | 阈值 / 判据 | 级别 |
|---|---|---|
| 单文件行数 | > 900 行且**本次仍在增长** | P2 |
| 单函数行数 | > 80 行 | P2 |
| 宽 `except Exception` | 必须二选一：记录日志，或注释说明为何可吞（`noqa: BLE001` **加**理由才算合规，裸 noqa 不算）。**已由 `tools/review_lint.py` RL001 守卫，零基线** | P1（守卫已阻断） |
| 析构/关闭路径吞异常 | 禁止。真实反例与修法见 §6.3 | P1（守卫 RL001 覆盖） |
| 新增第三方依赖 | 必须进 `pyproject.toml` 的 `optional-dependencies` 并说明"不装也能跑" | P1 |
| 类型注解 | 新文件带 `from __future__ import annotations`（多数模块已带，新文件必须带） | P2 |
| `print()` 调试输出 | 服务端代码用 `log`，不用 `print` | P2 |

### 5.2 HTTP API（`src/kitchen/api/`）

- 新增/删除路由 → 路由数变化必须同步 `requirements.json`，否则 CR-03 红。
- **每个写接口四件套**：鉴权（含角色）+ 入参校验 + 重复提交保护 + 审计。缺任一 → P1。
- 错误体格式统一（`code` / `message`），不得把 traceback 返回前端 → P0。
- SSE / 长连接：必须有限流（`MAX_SSE_CLIENTS`）与断开清理，否则连接泄漏 → P1。
- 时间参数一律 epoch 秒，禁用 `now` 作参数名（CR-07）。

### 5.3 存储与迁移（`storage/`、`migrations/`）

- SQL 只允许**标识符白名单 + 参数化值**。现有正确做法：`_quote()` 转义表名/列名，
  值一律走 `execute(sql, args)`。任何把用户输入拼进 SQL 的新写法 → **P0**。
- 禁止 `with conn:`（pymysql 的 `__exit__` 是 `close()`，已踩过坑，`backend.py` 有注释说明）。
- 迁移**只增不改**；编号连续；`migrate check` 必须绿。
- 方言分支（sqlite / mysql）必须给理由，不能"顺手写两遍"。

### 5.4 AI（`src/kitchen/ai/`）

- 六护栏逐条确认：只出建议 · 离线降级 · 白名单 · 逐次审计 · 不喂隐私 · 可复现（CR-08）。
  其中"只出建议"已由 `tools/review_lint.py` **RL002** 静态守着：
  `ai/` 里出现 `"approve"` / `"decision"` / `"amount"` 作为字典键即红。
- 模型调用必须有**超时 + 兜底**，且兜底路径有测试。超时无兜底 → P1。
- prompt 中不得出现 openid / 手机号 / token；`llm.py` 有第二道过滤，但**不能只依赖它**。
- 新增场景 = `AdvSpec` + `SCENARIOS` 一行（CR-09）。发现改动业务状态机 → P0。

### 5.5 前端（`web/`、`miniapp/`）

- `web/dist` 是构建产物，不入库；改了 `web/src` 就必须能 `npm run build` 通过。
- **三态齐全**：正常态 / 空态 / 失败降级态。只做正常态 → P1。
- 接口契约以 `tests/test_api_web_contract.py` 为准；前端字段名改动必须同 PR 改契约测试。
- 小程序：`miniapp_check.py` 必须绿；包体预算、tabBar 图标、`app.json` 页面注册齐。
- 可访问性：正文对比度达标、点击区 ≥ 44px、图片有替代文本（`docs/14` 有视觉规范）。
- 前端不得硬编码密钥；后端地址只允许出现在 `miniapp/config.js`，且标注环境。

### 5.6 测试（`tests/`）

- **禁止自证测试**：断言必须能独立推导。反例——用实现里的同一个常量去断言结果。
- 每个 P0/P1 修复**必须**带回归用例，命名体现现象（`test_close_commit_failure_raises`）。
- 时钟必须可注入，不得依赖真实 `datetime.now()`。
- 外部依赖必须可离线（`Inproc` 通道就是为此存在）。
- 用例总数不是质量指标；**变异一下代码还能红**才是。

### 5.7 文档与口径（`docs/`、`README.md`、`05_系统记录/`）

- 改数字：只改 `docs/requirements.json`，再 `python tools/consistency_check.py --fix`（CR-03）。
- **口径三不**：
  - 不说"生产级"（现状：单实例、1 GiB、裸 IP、无 HTTPS）；
  - 不说"全链路闭环"（必须区分"软件全链路 + 硬件接口预留"）；
  - 不说"模型已训练完成"（缺验证集的类别要写明，见 `vision_model_metrics.json`）。
- 新增文档必须进 `docs/README.md` 索引，否则 P2。
- 内部材料（含凭据位置、安全边界、未完成项）不写入公开仓库。

### 5.8 部署（`deploy/`）

- compose 参数必须与 1 GiB 机型匹配（buffer pool、`max_connections`、swap）。
- 备份必须**可恢复演练**，"备份成功"不等于"能恢复"（CR-04 的同类错误）→ P1。
- 改动 `deploy/` 必跑 `docker compose config` + `verify-cloud.sh`（CR-06）。
- 文档不得把"HTTP + 裸 IP + 测试 AppID"写成"可对外发布"（CR-13）。

## 6. 真实例子：好代码怎么夸，坏代码怎么提

审查的价值在于**引用具体行、说明具体后果**。以下例子全部取自本仓库当前代码，
可直接作为写评论的范本。

### 6.1 ✅ 值得夸：N+1 收敛并解释取舍

`src/kitchen/storage/backend.py` 的 `stats()`：

```python
# 用一条 UNION ALL 聚合查询**一次往返**拿全表行数（精确计数，区别于
# InnoDB information_schema.tables.table_rows 的采样估算）；表名来自
# 各自的系统表，可信，用方言对应的标识符引号转义后安全插值。这把原先
# N+1（每张表一条 COUNT(*)）收敛成 2 次查询（1 次取表名 + 1 次 UNION ALL）。
```

**这条该夸什么**：不只是"性能好"，而是它写清了**为什么不用采样估算**、**为什么插值是安全的**。
审查意见可以写：

> 💭 **P3 · 这个注释是范本**
> 一次往返 + 精确计数 + 插值安全性三件事都在注释里给了理由。后续改这段的人不用重新推一遍。

### 6.2 ✅ 值得夸：安全默认值 + 显式告警

`src/kitchen/api/auth.py` 签名验证"先重算再 `compare_digest`"；
`accounts.py` 使用演示默认口令时 `log.warning` 明示。

> 💭 **P3 · 演示默认值处理得对**
> 允许默认口令但启动就告警，符合 CR-13。唯一要求：PR 描述里同步声明这是演示口径。

### 6.3 ⛔ 该拦（已拦下并已修）：关闭路径吞掉 commit 异常

**审查时它是这样**（`src/kitchen/storage/backend.py` 修复前）：

```python
def close(self) -> None:
    if getattr(self, "_closed", False):
        return
    self._closed = True
    try:
        self._raw.commit()
    except Exception:
        pass          # ← 提交失败被静默吞掉
    self._raw.close()
```

**为什么是 P0**：这是"静默成功"的教科书形态——落库失败，调用方以为写成功了。
本项目历史上"备份成功但文件没落盘"就是同一根因。

**当时怎么提的**：

> ⛔ **P0 · 数据一致性：close() 吞掉 commit 异常**
> 行 220-223：`commit()` 失败被 `pass` 吞掉，调用方无法得知数据未持久化。
> 若这是有意的"尽力而为"关闭，也至少 `log.error`；更稳的做法是让 `close()` 抛出。
> 建议补回归用例：mock 一个 commit 抛 `OperationalError`，断言错误可见。

**修完是这样**（现行代码）：

```python
    try:
        self._raw.commit()
    except Exception as exc:
        log.error("关闭时提交失败，未落库的写入可能丢失：%s", exc)
        raise                      # 宁可报错，也不让数据悄悄丢
    finally:
        self._raw.close()          # 抛异常也要关连接，别泄漏
```

回归用例：`tests/test_backend.py::test_关闭时提交失败必须抛出而不是静默吞掉`
（断言异常上抛 + 连接仍被关闭 + close 保持幂等）。

而 `tools/review_lint.py` 的 **RL001** 会拦住任何退回裸 `pass` 的改动——
**这条从"人记得"变成了"CI 记得"**，这是标准落地的正确形态。

### 6.4 🔴 该提：超长文件继续增长

`src/kitchen/guest/service.py` 已有 1008 行（`api/state.py` 861、`api/actions.py` 858、
`finance/service.py` 728；**行数为 2026-11-19 快照，只说明量级**）。单看行数不是罪，
**本次改动还往里加**才是问题。

> 🔴 **P1 · 职责过载，本次不再加**
> 该文件已 1008 行、覆盖画像/客诉/证据/补偿四类职责。本次新增的 `_order_cap` 逻辑
> 属于补偿域，建议落到 `guest/compensation.py`（同域内拆分，不改对外接口）。
> 若确实要留在本文件，请在 PR 里说明为什么不拆。

### 6.5 🟡 该提（已在收口）：宽异常没有说明

工程里 `except Exception` 数量不少，其中一部分当时只有一行裸 `# noqa: BLE001`——
**noqa 不是理由，只是把 linter 静音了**。首次跑守卫时命中 13 处，现已全部补上
"为什么可以吞"（例如 `api/actions.py` 的"新增时记录尚不存在，取不到修改前快照属正常"、
`guest/chat.py` 的"订单已被清理，跳过该单继续找下一单"）。

**数量不写死在文档里**，用 `python tools/review_lint.py` 现查——它同时是判据和执行者。

> 🔴 **P1 · 宽异常缺少吞掉的理由**
> `except Exception:  # noqa: BLE001` 只声明"我知道"，没声明"为什么"。
> 半年后接手的人无法判断删掉这行会不会炸。
> 判据：**能说清具体异常类型的，就不要用 Exception**；确实要宽，就写一句中文理由。
> 修法见 `tools/review_lint.py` 的模块文档（合规/不合规两种写法对照）。

## 7. 评语规范

一条合格的审查意见 = **级别 + 结论 + 为什么（行号/证据）+ 怎么改 + 是否需复测**。

**不合格**：

- "这里不太好吧" —— 没有级别、没有理由、无法执行。
- "建议重构一下" —— 重构到什么程度算完？谁判断？
- 只丢一个链接 —— 审查者要替作者读懂上下文。

**合格模板**：

```
{级别} · {一句话结论}
行 {n}：{现象}。
为什么：{后果，最好能指向本项目历史事故或规则编号 CR-xx / R1-R6}。
建议：{可执行的最小改动；给 1-2 个选项让作者选}。
复测：{需不需要复审这一点 / 需要哪个用例证明}
```

**五条纪律**：

1. **一次给全量意见**，不要分十轮挤牙膏——作者会反复重跑 CI。
2. **不重复上一轮已达成一致的结论**；有分歧就升级到"记录并决定"，不要循环。
3. **对事不对人**：说"这个 `pass` 会吞掉 commit 失败"，不说"你总是乱写异常处理"。
4. **能引规则的引规则**（`CR-08` / `R5`），让争论从"我觉得"变成"标准怎么写"。
5. **夸要具体**（§6.1 那种），泛泛的"写得不错"没有信息量。

## 8. 流程：从改代码到合并

### 8.1 分支与提交

| 项 | 约定 |
|---|---|
| 分支名 | `feat/<域>-<短描述>`、`fix/<域>-<短描述>`、`docs/…`、`chore/…`、`refactor/…`，域取 `api` `guest` `finance` `compliance` `ai` `storage` `mqtt` `tft` `miniapp` `web` `deploy` `vision` |
| 提交信息 | Conventional Commits（现状已在用：`fix(ci):` `feat(vision):` `docs(vision):`） |
| 一个 PR 一件事 | 混入无关格式化/重命名 → P1，要求拆出 |
| 禁止直推 main | 唯一例外：hotfix 且事后 24h 内补 PR 说明 |

### 8.2 PR 体积红线

| 指标 | 目标 | 超过怎么办 |
|---|---|---|
| 净变更行数 | ≤ 400 | 先拆；确实不可拆（如迁移+模型联动）在描述里写"为什么不能拆" |
| 变更文件数 | ≤ 10 | 同上 |
| 单 PR 涉及业务域 | ≤ 2 | 跨 3 域基本等于两件事，拆 |

> 大 PR 的审查质量会断崖下降：审查者在第 500 行之后基本只看格式了。

**已工具化**：`python tools/pr_size.py`（或 `tools/ci.py` 最后一关）会算出变更行数 /
文件数 / 域数并提示超标。**刻意不阻断，只提示**——硬拦的最常见后果是"拆成两个各自
不自洽的坏 PR"，比大 PR 更糟。真要拦，用 `--strict`。

默认口径是**基线 → 当前工作树**：已提交 + 已暂存 + 未暂存 + 未跟踪新文件（忽略文件不算）。
只看已提交部分用 `--committed-only`。这条是审查 P2-6 的修复：旧版只算 `base...HEAD`，
在"攒满工作区再提交"的工作方式下会报假绿灯——**守卫说绿比没有守卫更糟**。

### 8.3 作者自检（提审前必做）

1. 本地跑 `python tools/ci.py`，把 `X/X 关通过` 贴进 PR（有 `SKIP` 也要贴，别只贴通过数）。
2. 填完 `.github/pull_request_template.md`（含 R1–R6 自检清单）。
3. 自己先当一次审查者：用 §3 清单过一遍 diff，把能自己发现的问题先改掉。
4. 确认没有 `print` 调试残留、没有临时文件、没有注释掉的旧代码。

> 第 3 步不是形式主义：**作者自审能拦掉约一半的 P1**，这是投入产出比最高的一步。

### 8.4 审查轮次与 SLA

| 事件 | 时限 | 说明 |
|---|---|---|
| 首次反馈 | 24 h 内 | 超时则作者可升级给项目负责人 |
| P0 修复后复审 | 只复审该点 | 不做全量重审，避免拖时间 |
| 审查轮次上限 | 3 轮 | 第 3 轮仍有 P0 → 打回重做设计，不在评论里继续磨 |
| 紧急修复（线上挂） | 2 h 内 | 可先合并后补审，但必须在 24h 内补 PR 并复盘 |

### 8.5 合并门禁（全部满足才可合并）

- [ ] `tools/ci.py` 全绿（含 pytest / 迁移 / web_check / miniapp_check）
- [ ] `⛔ P0 == 0`
- [ ] `🔴 P1` 全部已修，或已开 issue 并写明理由与期限
- [ ] PR 模板填完（改动类型 / 影响面 / 本地验证 / 云端验证 / 迁移 / 数字）
- [ ] 涉及 `deploy/` 时附 `verify-cloud.sh` 结果
- [ ] 涉及 DDL 时附非空存量卷迁移结果
- [ ] 审查结论已勾选（见 §8.7）

### 8.6 合并与回滚

- 合并方式：**squash**，`main` 保持线性，一条提交对应一个 PR。
- 合并后删除分支。
- 回滚优先 `git revert`，**不用** `reset --hard` + `push -f`。
- 数据类改动（DDL / 批量写 / 迁移）必须同时给**回滚 SQL 或恢复步骤**，否则 P0。

### 8.7 审查结论（写进 PR 末尾）

```
## 审查结论
- 审查人 / 日期：
- ⛔ P0：0 条
- 🔴 P1：N 条 → 已修 / 已开 issue #x（期限）
- 🟡 P2：N 条 → 已记入债务表
- 结论：☑ 通过　☐ 有条件通过（P1 限期）　☐ 打回
```

### 8.8 事故复盘（合并后才发现的问题）

五栏固定格式，写在 `05_系统记录/`：

> **现象** → **根因** → **修复** → **回归用例** → **可预防规则**

第五栏如果指向一条**新的、可自动判的**规则，就落成 `tools/` 里的守卫；
如果是**人审才能判的**，就升级为本文的一条 `CR-xx`。
**没有第五栏的复盘等于没复盘。**

## 9. 单人项目的现实版（关键）

本项目当前是单人开发，"找个人来看"不现实。用**等价机制**替代第二双眼睛，
但必须承认它比真审查弱——所以**高风险改动不能用自审替代**。

### 9.1 自审的三条替代机制

| 机制 | 做法 | 什么时候用 |
|---|---|---|
| **24h 冷却自审** | 写完不当场合，隔天用 §3 清单重读 diff | 所有非 trivial 改动 |
| **换视角自审** | 以"答辩老师会问什么"/"接手新人会误解什么"的角度读 | 涉及口径、架构、AI 的改动 |
| **AI 预审** | 把 diff + 本文清单交给助手，先产出 P0/P1 候选清单，人做最终裁决 | 大 PR、跨域改动 |

> AI 预审的红线：**AI 只能提候选，不能给"通过"结论**；裁决权在人，
> 因为 AI 不知道答辩现场会被问什么。

### 9.2 强制"第二双眼睛"的改动（不可自审）

以下六类即使单人也要走外部审查（导师 / 同学 / 有经验的朋友，哪怕只看 30 分钟）：

1. 凭据、密钥、账号体系、权限矩阵的改动（CR-01 / CR-11）
2. 数据库迁移与备份恢复路径（CR-05）
3. AI 六护栏相关代码（CR-08）
4. 任何删除/覆盖数据的操作
5. 对外发布相关（域名、HTTPS、小程序提审、公开仓库内容）
6. `deploy/` 里的安全边界（端口、口令、挂载）

理由：这六类出错的代价**不可逆**，而自审的盲区恰好就在"我以为我懂了"。

### 9.3 审查台账

路径：`05_系统记录/代码审查台账.md`（模板见附录 B）。
一行一个 PR，记：编号 / 日期 / 范围 / 审查方式（自审·外部·AI 预审）/ P0·P1 数 / 结论。
作用不是考核，是**让"零评审"这件事可视化**——一旦台账连续空着，就说明流程已经死了。

## 10. 度量：只看四个数

| 指标 | 定义 | 目标 | 超标说明 |
|---|---|---|---|
| PR 中位体积 | 净变更行数中位数 | ≤ 250 | > 400 说明拆 PR 纪律失效 |
| 首轮反馈时长 | 提审 → 第一条意见 | ≤ 24 h | 拖长会导致作者并行改别的，冲突变多 |
| **P0 逃逸数** | 合并后才发现的问题数 | 0 | 这是**唯一真正重要的指标**，其余都是过程指标 |
| revert 次数 | 每月回滚提交数 | ≤ 1 | 连续两月 > 1 说明门禁形同虚设 |

**不要统计**：评论条数、审查时长、P3 数量。这些数字一被考核就会变形
（审查者开始凑条数，作者开始为 P3 吵架）。

## 11. 30 天落地计划

| 周 | 只做一件事 | 完成标志 |
|---|---|---|
| **W1** | 建立"分支 + PR + 自检"习惯，**不改任何代码** | 至少 2 个 PR 走过模板，CI 绿才合并 |
| **W2** | 启用 P0/P1 分级与 SLA，开始记台账 | 台账有 3 行；每个 PR 有级别化意见 |

| **W4** | 把可自动判的规则工具化（见下） | 至少 1 条 CR 从人审移入 CI |

### W4 工具化清单（2026-11-19：1–3 已实施，4 待办）

| # | 项目 | 状态 |
|---|---|---|
| 1 | **审查静态守卫 `tools/review_lint.py`**：RL001 宽异常吞掉必须写理由（含裸 noqa）；RL002 AI 输出不得出现 `approve`/`decision`/`amount` 键。**零基线**（不设债务豁免），已挂进 `tools/ci.py` 第一关 | ✅ **已实施**（11-19）：首发命中 13 处，已全部整改；新增回归用例 1 条 |
| 2 | **`ruff` 最小规则集**：只开语法级 `E9,F63,F7`（配置在 `pyproject.toml [tool.ruff]`）。**没装则 SKIP，不伪造 PASS**；GitHub Actions 已 `pip install ruff` 真跑 | ✅ **已实施**（11-19，配置级）：本机无法安装 ruff（网络不通），故**本地未实跑验证**；用 `compileall` 全绿 + 全仓仅 1 处真 `%` 格式化（合法）估过误报面为零，首次 CI 运行需留意 |
| 3 | **PR 体积守卫 `tools/pr_size.py`**：>400 行 / >10 文件 / >2 域 时提示；**默认不阻断**，`--strict` 才拦；默认含工作区未提交与未跟踪文件，`--committed-only` 只看已提交 | ✅ **已实施**（11-19）→ **修正口径**（11-20）：审查 P2-6 修掉假绿灯，四条路径实测 |
| 4 | **审计脱敏守卫**（CR-12 的可自动部分：新敏感字段未进 `_MASK_KEYS`） | ⬜ 待办 |

**顺序原则**：先有习惯，再上工具。反过来会得到"工具很全但没人用"。
**另一条原则**：新守卫必须**零基线**上线——一旦允许"存量豁免清单"，
三个月后清单比代码还长，守卫就废了。存量先修干净（本次 13 处约 20 分钟），再开门。

**第三条原则（本次踩到的）**：**没跑过的守卫不许写成"已通过"**。
ruff 本机装不上，所以它在 `tools/ci.py` 里是 `SKIP` 而不是 `PASS`——
"跳过"和"通过"在汇总里分开计数，就是为了不让这类沉默被当成绿灯。
